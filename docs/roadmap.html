The goal

One sentence per step, in the first person

The product stated as what a person does, not what the engine does — which is why “It works” is a step rather than an outcome. Everything below exists to make this list run end to end without a person writing the middle of it.

  3. Step 3I build tests
  4. Step 4I build code

The pipeline

Steps 2–4 are three commands

Each reads documents and writes exactly one thing. Rectangles with a heavy outline are commands; everything else is a document on disk.

  • command
  • story

Two things the shape is saying. First, architecture.yaml is read twice, by two different commands — it is not consumed and discarded at the top, which is why it is drawn as an input to each rather than as a document that flows downward. Second, every command has exactly one output. Nothing writes two things, and nothing writes backwards.

What “build” means

Two inputs, one transform, one output

Tests say what must be true. The architecture says where the code may go and what it may be built with. The build step has to satisfy both at once — it may not make a test pass by putting code somewhere the architecture does not declare.

Milestones

Four cards, two already ticked

In board order, left to right.

✓Done

I have code and Playwright / CLI tests

The starting position: a working system with a real test suite, written by hand.

✓Done

I can generate code from tests

build code closes the loop from a failing test to production source. This is the milestone that proved the direction: if the tests are the specification, the code is derivable.

Open

Generate GWT tests from scenarios.yaml

I can generate GWT tests from scenarios.yaml

Given/When/Then tests rendered from the registry rather than authored — the registry stops being a document about the tests and becomes the thing they are generated from.

Open

Create remaining scenarios with all artifacts

Create remaining scenarios with all artifacts: vocabulary, features, steps, etc.

I can generate GWT tests, steps, judgements from scenarios.yaml

The difference from the previous card is the word steps. That one generates the test; this one generates the step definitions the test binds to, and the judgements that grade what no comparison can settle. When it lands, a scenario written in the registry is executable without anyone opening a .go file.

Decision log

Why the board is drawn the way it is

  • The five-step list is written in the first person on purpose.

    It is the user's experience of the product, not the engine's control flow — which is why “It works” is a step rather than an outcome. A roadmap phrased as engine stages would have hidden that the whole point is what the person does not have to do.

  • scenarios.yaml appears twice in the pipeline drawing.

    Same file. The loose one at the top is the registry as an input the author may already have; the connected one is the registry as the thing us apply writes.

  • Milestones 3 and 4 are separate cards even though both say “generate GWT tests”.

    Splitting them is the useful part: 3 is generating the test, 4 is generating what the test binds to. Collapsing them would hide that the first is deterministic codegen and the second needs a model.
