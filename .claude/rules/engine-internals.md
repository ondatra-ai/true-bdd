# Engine Internals

## build tests / build steps / build code, in depth

- `build tests` — deterministic Registry codegen only: one `func Test<Key>` per Scenario into its `path:`. `--fix` writes stale files; without it regenerate-and-compare refuses stale files. Registry, path, renderer and step-shape refusals precede rendering; Catalogue phrase refusals apply only to template hosts. Concept hosts render free text. It does not read step definitions, run AI, offer a fix menu or start a test runner.
- `build steps` on a template host — lists missing phrase × suite Items and answers `D: step-coverage` in-process without AI or a runner. Inventory includes a phrase mapped to the suite's service or used by one of its Scenarios. `--fix` uses `runner.Spec` and the shared Fix loop: preflight term lists, Public interfaces, mappings and architecture-derived protected test grants; write every registration and pending function using the Catalogue's capturing variant; compile all skeletons before AI. The complete phrase context is embedded in both proposal and writer turns. Writers change only the selected body, imports and shared State. Each completed apply checks source shape, suite compilation, one definition with the engine's pattern and no pending sentinel; failed findings return to the same Item. A nonempty `interface_cannot_serve: {phrase, lacks}` confirmation stops immediately with a distinct architectural error. Convergence runs whole-suite Step coverage, package-qualified generated-test listing and one suite run in a Host project copy without every service path, VCS metadata or scratch. Each Scenario must fail at an executed definition (the harness's numbered step failure diagnostic). Compilation, bring-up, skipped or missing results are distinct failed checks naming the Scenario. A green Scenario returns all its phrases' Items written in this run together, with the finding, through runner.Spec.CheckConvergence and the engine's bounded outer walk. Per-Item apply counts persist across these checks; a green Scenario without a written Item stops distinctly. BUILD STEPS COMPLETE follows only a successful red check. The pipeline is `us refine`, `us apply`, `build tests`, `build steps`, `build code`.
- `build steps` on a concept host — scans definitions before grouping the deduplicated unbound texts per suite and block, excluding `judge:` and `llm:`. The `Q:` group protocol takes the best and runner-up scores and reuses the link threshold selector and ambiguity verdict. Its checklist `config.grouping_batch_texts` defaults to 800, measured for `claude-opus-5` and this answer format; the engine divides larger blocks into the fewest balanced batches. Missing, repeated or unknown indexes, invalid rankings and output-cap errors crash. Semantic link failures name every step and ambiguous concepts before any skeleton. Each concept and suite is an Item; every grouped concept must have a binding for the service, rejudged using `scen check`'s exact binding Prompt and evaluator. Missing or ambiguous bindings name the concept and stop. After both passes, the distinct `ErrPatternProposalPending` stops the command without writing definitions or generated tests; proposal and skeletons are deliberately a later slice. Artifacts remain in host tmp. Both bare and `--fix` runs take this path.
- `build code` — starts every outer walk with full discovery through `testing.commands.replay`, yielding zero Items or one whole failing set (`commands.BuildCodeItem`). Its `tests-pass` built-in `D:` Prompt answers through `runner/check_cell.go`, without a validation turn; all latest member verdicts must pass. The fix turn proposes one plan naming changes, files and served tests. The apply turn is the writer: it gets the same set, deduplicated phrases and words, all matched Scenarios and steps, Specification paths, declared service edit roots, and codex and Claude whole/selected replay forms. It reads the Specification and harness, implements the service, tests each part and every set member, and reports changes and observed passes. No prompt budget is stated. Every completed apply (including `applied: false` and the terminal attempt) reruns the remaining set in `PostFix`/`PostNotApplied`, in one framework runner start. A successful provider response missing the result block (`ErrFixApplierNoContent`) follows `PostNotApplied` only for `build code`, keeps files and logs one WARN carrying the result path. Started codex non-zero/empty outcomes and Claude non-zero/error-result/empty outcomes also preserve files, warn once and follow PostNotApplied. Start failures, engine refusals before spawning, other commands and roles retain fatal handling; malformed extracted blocks and missing `applied` retain their existing handling in every command. The writer ends its final message with the confirmation block in the message itself; the engine saves the block at its heading's path, which the writer never writes. Selectors are joined by alternation; Go `<build>` or Playwright `<startup>` makes the rerun unfiltered. Members need their own passing result; missing/skipped results stay failing with a did-not-run finding. Passing members leave; grouped evidence uses build-tests runtime normalization but retains the whole first output and every member id. `BeforeEvaluate` leaves the verdict to `D:`. The walker attempt counter and outer bound are unchanged: allowance two still permits three applies; membership changes never reset the same Item's counter. The terminal apply is rerun but still fails at the bound even if the rerun passed. Fresh outer discovery catches previously green regressions. Exit ends the Item. Optional Specification documents warn and are omitted when unavailable; exact module-aware Go identities alone match Registry Scenarios. The mandatory `testing.commands: {record,replay,live}` block has no built-in defaults; native machine-output flags and config-directory cwd are retained by engine runners. Static refusals precede subprocesses; spawn-only errors report `Cannot run test suite` / `Cannot run suite` as `runner.Reported`. Build-code write roots are the failing set's service paths and exact `writable` entries, plus host tmp; unknown-service failures use all services. Existing folders grant their subtree; absent writable entries remain exact leaves unless a trailing slash declares a folder. Before discovery (and before evaluating the remaining set), the engine refuses outside or parent-traversing paths, patterns and overlap with protected tests: `tests/`, Registry suite directories, the in-host `testing.config` directory and named Go command package directories (`./dir` or `./dir/...`, relative to the runner cwd), step definitions included. Broad `./...` names no separate test directory. Command package directories inside a service path, including its `_test.go` files, stay writable service code; reserved tests, Registry and config directories take precedence. The plan's build-code-only schema and the writer's confirmation carry `impossible: [{path, reason}]`: only a truly impossible repair qualifies, after seeking a permitted solution. A nonempty verdict retains edits, reruns the remaining set once and returns `ErrImpossibleWork` with files, reasons, remaining failures and the manual-or-writable remedy, through the walk's error path before any COMPLETE banner. An empty list preserves ordinary retries. Document commands still reject `applied: false` before their commit hooks.

**Startup refusals**: every command reports precondition failures as `Cannot start: …` on stdout plus a `Refusing to start` slog record — the BDD judge reads the log, not the terminal, and `stdout_regex` matches stdout alone. All go through `runner.RefuseStartup`, a container `cmd` cannot build among them (`containerFor`), except two whose messages Scenarios pin: the `docs:` check (`Refusing to start: checklist documents unsatisfiable`, inline in `validateSpec`) and a document key `cmd` cannot resolve (`Refusing to start: document unresolvable`, `refuseUnresolvedDoc`). An error already diagnosed by the code that produced it is wrapped in `runner.Reported` so it is not announced twice. A walk that stops mid-way (a Prompt fixed more often than `config.max_apply_attempts` allows, a failed AI turn, a check that cannot answer) is logged once more by `runner.Run` as `level=ERROR msg="Walk stopped"` with the command and the error, since cobra prints the error only to stderr (`fix-loop-bounds-002`).

## Model tiers and providers

The engine drives two agent CLIs — `claude`, `codex` — picked per checklist role. `engine.models` binds tiers (`xhigh`, `high`, `coder`, `quick`) to `"<cli>:<model>"` (split on the FIRST colon only); `engine.default_prompt_model` / `default_fix_model` / `default_apply_model` name each role's fallback tier. Per-cell resolution: prompt override (`model:`/`fix_model:`/`apply_model:`) → checklist `engine:` block → `engine.default_<role>_model`. Anything unresolvable is a startup error, never a silent substitution.

- **Turn lifetime (ADR-0025):** the router adds no deadline to any role or CLI. Every turn runs with the caller's context; cancellation stops its process group and descendants and remains fatal. No time, turn, token or cost budget is added to requests, prompts, checklists or templates.
- `internal/domain/models/provider/` owns the vocabulary (`ModelRef`, `Tier`, `Registry`); the registry is validated once in `bootstrap.newAIRouter`. `adapters/ai/router.go` is the only `ports.AIPort` implementation.
- `ExecutionMode.WriteGlobs()` supplies the write patterns for Claude's guard and codex's apply profile; `AllowsBash()` also guides Claude tooling. The router independently selects codex apply confinement by role, leaving plan and validation read-only.
- The fix generator and applier never see the prompt; the evaluator resolves their tiers and carries them on `ValidationResult.FixModelTier`/`ApplyModelTier`.
- **Claude build-code writer (2.1.285, ADR-0022):** only this applier requests `TurnOptions.ClaudeWriter`. The wrapper uses generated `--settings`, `--restricted`, an explicit six-tool inventory (MultiEdit is named but absent in 2.1.285), default permission mode and no safe mode. `claude-guard --policy <generated JSON>` receives every PreToolUse payload and explicitly grants only canonical foreground Bash or confined file tools. Bash has no permission allow pattern; both Bash timeouts are 600000 ms. Read roots are the host, GOROOT, the architecture-declared library graph and its exact version metadata, and this session UUID's tool-results directory. A module cache inside the host stays restricted to that graph. The generated policy and library-download scratch are protected from writes. Claude's replay remains unconfined with network for model trials (ADR-0028, Q15). Searches outside the host reject ancestors of excluded module copies; Glob also checks its fixed pattern root and denies parent traversal. Writes derive from the execution mode's roots, excluding the generated settings/policy directory. User/project CLAUDE.md, automatic memory, skills, installed plugins, commands, workflows and MCP stay disabled. Default sign-in is retained because an empty config dir was signed out. The applier renders Claude foreground completion or codex native polling directly from the shipped template. Started Claude non-zero exits, error results and empty replies carry `errors.ClaudeTurnError`; only the build-code applier recovers them, with one WARN and `PostNotApplied`. Stream cost survives failed results. Start failures remain fatal. Other Claude turns retain their arguments and share the unbounded, cancellable lifetime.
- **codex applies (0.162.1, ADR-0021 and ADR-0024):** the router sets `Request.CodexApply` for every codex apply role regardless of command or tools. `TurnOptions.CodexWriter` remains build-code-only and selects replay forms and recovery. Generated per-turn `CODEX_HOME` copies only private `auth.json`; its profile denies commands access to the shared host tmp/codex-homes subtree for all turns and runs; auth.json is removed on preparation or turn completion, success or failure, and cleanup errors are reported. The profile denies every filesystem path outside the host except `:minimal` OS runtime, GOROOT, the architecture-declared library graph and exact version metadata, and the explicit runtime grants below. The module cache is denied by default with narrower library read entries; its cache/vcs subtree, protected library-download scratch, and implicit `/private/tmp`/`/private/var/tmp` scratch are denied; host roots take precedence where nested. The mode's file, directory and configured-glob roots and host tmp are writable. Existing files stay files; literal directory roots and file parents use rooted creation. Configured globs allow matching new files even without existing matches. Terminal `/**` retains its literal subtree grant; other wildcards grant the narrowest literal directory and enforce the original patterns after every turn. Newly created non-matching files are removed; a pre-existing non-matching file changed, deleted, renamed or given different permissions fails the turn with one WARN naming it. Overlapping grants authorize their union; these violations are fatal even for build code. Generated homes are excluded from comparison; malformed patterns, host-root grants and escapes refuse (ADR-0024). Source-root symlinks escaping the host are refused. Command environment inherits nothing: controlled PATH, HOME/TMPDIR/GOCACHE under host tmp, Go roots, offline proxy/sumdb, local toolchain, disabled telemetry/CGO and `-trimpath -buildvcs=false`. Optional installed node/npm/npx/docker binaries, npm's validated package, Mach-O dependencies and their installation symlinks are explicit read grants; Homebrew opt directories permit link metadata, with unrelated canonical targets denied. npm/npx JavaScript package roots require package.json naming npm and resolved bin/npm-cli.js or bin/npx-cli.js, outside the host, authentication and sensitive home roots enumerated in ADR-0024; otherwise the runtime is refused with a WARN and no link or grant. Generated runtime-bin links, offline npm cache/config, Docker config and all writable runtime state stay in scratch. No Docker daemon or socket is granted; `OPENSSL_CONF=/dev/null` avoids outside OpenSSL configuration. No outer sandbox. Generated config suppresses user config/MCP/web/history/AGENTS.md/host skills/plugins/apps; high reasoning, configured window 1050000 (1M unverified). `--json` stdout is archived separately from stderr; `-o` remains the answer. Drill audit reads commands and file changes without inferring read success. Started non-zero/empty/missing-answer outcomes carry `CodexTurnError`; build code alone preserves edits, warns once and reruns `PostNotApplied`. Start failures stay fatal. No codex stall watch. Planning and validation keep argv, environment and read-only sandbox; other commands' confined applies retain fatal failures. Cassette filtering excludes generated homes and shell/build scratch.
- **codex gotchas (verified live, codex-cli 0.162.1, #165):** `--output-schema` refuses a schema whose `required` leaves out any property, which claude accepts, so `CodexProvider` lists every property there before writing the schema file. codex writes its own answer file, so the cassette carries it: it is `-codex-answer.txt`, since a `.md` there fails alint's `text-final-newline` (codex ends its message with no newline).

## Prompt data contract

`docs/architecture/architecture.yaml` states the data each configured prompt template reads under `architecture.prompt_data`, including its source and every transformation before rendering. A change to any transformation stated there updates its `prompt_data` entry in the same change. Keep shared anchors accurate for every template using them. The field-inventory guard in `internal/infrastructure/template/prompt_inventory_internal_test.go` compares template reads with those entries in both directions; it does not verify shaping.

## Build identity

`version` is a plain terminal answer: exactly `true-bdd version <version> commit <commit>` and a newline, without loading configuration, installing logging or creating files or directories. Commands that install the engine log, including `init`, emit one INFO `Engine started` record with `version` and `commit` before any other record. `engine-entry-005-version-reports-build` pins the file-free answer; `build-tests-files-002-stale-test-regenerated` pins the start record without an AI turn.

## Package notes

- The engine owns all code it uses from this repository: `internal/infrastructure/{console,disk,logging,shell,enginelog}` are its IO channels and log vocabulary; `internal/infrastructure/cli/` exposes the spawn vocabulary and typed wrappers `claude`, `codex`, `git` (environment scrubbing), `gotool`, `spec` and `truebdd`. Only the shell imports `os/exec`; only those explicitly named wrappers import the shell. Logs use the engine's logging channel, files its disk channel and terminal descriptors its console channel. The domain imports none of these implementations. `pkg/` remains independent code for tests and tooling and the engine never imports it. The `Engine owns repository code` gate scans all engine Go imports, including tests and hidden build variants; the drill records its result in `engine_imports`. CLI argv/stdin remain the byte contract stated in `docs/architecture/architecture.yaml` (`dependencies[].invocation`); change an invocation and that statement together.
- `internal/app/generators/scenariogen/` renders registry → Go test. `BuildPlan` refuses the whole registry before writing a byte; `Render` always runs `format.Source`; `Write` refuses a target without the generated marker. Its template is `//go:embed`ed (it must compile against bddgo's API), not under `templates/`.
- `internal/infrastructure/stepcoverage/` parses each suite's `steps/` package and resolves which registry steps bind to nothing. Its mirror of bddgo's resolver is checked by running both: with the suites green, engine and runtime must agree on every scenario.
- `internal/app/checks/` holds the built-in checks a `D:` prompt names (ADR 0015). A command's `runner.Spec.Checks` is the `checks.Set` of checks that read its Item (`checks.ForScenarios` for `scen check`, `checks.ForStories` for `us refine`), so a new check is one entry there; a command with none refuses every `D:`. The runner answers a `D:` Cell itself (`runner/check_cell.go`), never through the evaluator, and saves the verdict as the JSON a schema-bearing turn leaves, under the Cell's usual artifact names, so the coverage census credits both alike. `PromptWithContext.Index` is the FILE position: `D:` prompts walk first (`walkOrder`), but artifacts and report rows keep file numbering — so inserting a `D:` above existing `Q:`s renumbers them, changes their result paths, and re-hashes every cassette of that checklist; append it instead. A check's `Docs` lists the document keys it reads, and a `D:` whose effective `docs:` omits one is a startup refusal: the check would find nothing there and pass unchecked.
- The closure checks `step-phrases`, `declared-terms`, `term-mappings` and `step-definitions` (spike #133's catalogue), with `public-interface` and `phrase-mappings` (#239, #240) beside them in `internal/app/checks`: `internal/infrastructure/product` reads the product document's `catalogue:` or `concepts:`, role names and `glossary:`, the only parts the engine decodes; `internal/domain/models/catalogue` compiles each template to an anchored regexp and reviews a run of `catalogue.Step`s (block plus keyword-less text, from `RegistryScenario.Phrases`), so `build tests` and `us refine` can reuse it on their own Items. `Declarations` lists the (template, term) pairs of the steps that match exactly one template, which `ReviewTerms` holds to the glossary. `term-mappings` holds the same pairs to the architecture's `terms:` (`architecture.LoadTermMappings`, `ReviewMappings`), and `step-definitions` holds the templates to the suite's step definitions: `stepcoverage.LoadSuite` folds `StepsDir(path)` as `Scan` does and `Suite.Bind` lists every definition a text matches, and `(*Catalogue).Correspond` relates templates and definitions over the steps of every claimed Scenario sharing that suite, which is why `ScenarioCheckData.Registry` carries the whole Registry whatever ids were selected. A check's error stops the walk and is logged as `msg="Check could not answer"`, since cobra prints it only to stderr. All four closure checks share `checks.activation`: no `catalogue:` key, or a Scenario with empty `user_stories`, passes as "not checked". `scen check --fix` writes a closure fix to the term documents, the product and the architecture document, and a model Prompt's fix to the product document or the Scenario's own Registry entry: `commands/fix_documents.go` seeds `tmp/<run>/<key>.yaml` per term document the host has and one for the Registry, the applier edits that copy in EditMode (codex apply confinement grants the mode's scratch writes; an existing single-file source root stays a file), and `PostFix` puts a changed copy over the document once it parses and its catalogue and glossary, its word mapping, or its Scenarios (the same ids) load; a changed Registry is reloaded into every walked subject in place, so the restarted walk asks about the Scenario as it now reads. A fix stands only once a walk converges: a run that ends otherwise (out of walks, the exit choice, a walk that stopped) puts every document it wrote back as it read before the walk (`commands.fixLedger`, `fix-loop-bounds-004`). Its fix-generator template renders `FailedCheck.Context`, the only place a `D:` finding reaches the model; the other commands' templates do not. For legacy cells, each of the four fix templates branches on `eq .FailedCheck.Check ""` (the applier's on `eq .Check ""`, which the runner fills from the failed result): a `Q:` Prompt's fix gets the Scenario-rewriting text and the Registry's working copy, and the `else` branch holds the closure text byte for byte. Inside it, `FailedCheck.Check` (the `D:` check's name) describes the glossary for a `declared-terms` fix and the word mapping for a `term-mappings` one, keeping the `step-phrases` prompt byte-identical: a new check's guidance goes in its own branch, or the cassettes of `scen-check-fix-001`, `-002` and `-003` re-hash. The closure applier templates name `architecture.terms:` only when `.Subject.Writes "architecture_yaml"`, which no `step-phrases` or `declared-terms` fixture has. `us refine` walks a `template.StoryRefineData` (the Story embedded, so its templates read the Story's fields unchanged) and offers only `step-phrases`, which holds every acceptance criterion's steps to the catalogue, one context line per criterion, whenever a catalogue is declared: there is no claiming for a Story. Under `--fix` it seeds the term documents' working copies as `scen check` does, its applier runs in EditMode, and a failed `D:`'s fix goes through `Spec.PostCheckFix`, which commits the changed copy and keeps the Story's version, instead of `PostFix`, which reads the applier's reply as the next Story body. Its four `us-checklist.fix-*` templates branch on the failed check the same way, the `Q:` branch byte for byte the old text (us-refine-fix-002 replays across the change).
- `internal/infrastructure/architecture/loader.go` decodes ONLY `testing:` (`framework`, `config`, `commands`, `libraries`) and each service's `name`/`path`/`language`/`writable`/`libraries`/`public_interface`; it also loads `phrases:`, while `term_mappings_loader.go` reads `terms:`. Other sections under `architecture:` stay undecoded — only `go run ./scripts/cmd/linters schemas` would notice a typo there.
- **A new checklist costs a fixture run per branch.** `pkg/testkit/cmd/coverage` requires the checked-in `baseline.yaml` to cover EVERY (prompt × pass/fail) branch of every shipped checklist (`assertBaselineComplete`), and `TestUniverseCensus` pins the Q/F/branch counts — so an 8-prompt checklist needs one fixture scenario designed to pass all 8 and one designed to fail all 8. The walk continues past a failure when no `F:` exists (`CellFailedNoFix` → `idx++`), which is what lets one run cover eight branches. A prompt with an `F:` has a third, `fix`, branch, which only a `--fix` run that fails the prompt, applies the fix and converges covers: the `scen-check` quality and model closure prompts get one recorded fixture each, narrowed to that prompt by `checklist-prompts.yaml` (one per pinned prompt in `declaredSelections`). A fixture's own checklist credits a shipped prompt when its question or check, rationale, `F:` and docs are the shipped ones verbatim (`EvalKey`), which is how `scen-check-fix-001` to `-004` cover the four closure checks' fix branches: copy a shipped prompt into a fixture's checklist byte for byte. Regenerate after a full replay: `go run github.com/ondatra-ai/true-bdd/pkg/testkit/cmd/coverage -session <s> -write-baseline`. `Baseline.Write` is fail-closed on HARD diagnostics and `-rebaseline` does NOT lift that; eight fixtures (`build-code-command-not-executable`, `build-code-jest-no-tests`, `us-apply-{malformed-scenarios,missing-story,shared-prefix,story-id-mismatch,story-without-acs,unshaped-criterion-id}`) emit one every session, so delete their run dirs from the scanned session first — they contribute no coverage, having no AI turns.
- `true-bdd/` schemas are host lint contracts, not engine inputs — only `go run ./scripts/cmd/linters schemas` enforces them, though the engine reads the product document's `catalogue:` or `concepts:`, role names and `glossary:` and the architecture's `terms:` itself, and refuses one it cannot decode; the pairing key is the WHOLE document key, underscores included (`architecture_yaml-schema.yaml`), and a schema whose key names no document HARD-FAILS the gate.

## Run-only model overrides

Every AI-turn command (`us refine`, `us apply`, `scen check`, `build steps`, `build code`) declares repeatable `--model <tier>=<cli>:<model>` flags. Lazy bootstrap validates the loaded tier table and role defaults first, then validates all overrides against declared tiers using the config's model-reference parser; duplicate tiers, undeclared tiers and invalid references refuse startup with exit 1 before any turn. The resulting in-memory registry changes only the named tiers, preserving Prompt → checklist → role-default selection. Each override logs once at INFO with `msg="Model tier overridden"`, `tier`, `from`, `to`. Apart from logs no override is written to a file, and none enters a spawned process's environment; the resolved model travels as its CLI argument. The drill accepts only repeated `--model` value pairs after `build steps --fix` or `build code --fix`, and none after `build tests --fix`; it keeps them in the run's argument record and forwards values unchanged through typed wrapper options. Engine startup owns semantic validation; deterministic `build tests` has no `--model` flag.

**Concept judgements (#257):** `with.concepts` selects link, group, bindings, sketch or words on a Q Prompt. Template hosts omit link/group/binding/word cells; Prompt 12 keeps its old bytes there. Concept links are current-walk Item evidence, never Registry data. Word judgements require that walk's successful link and a complete verdict for every linked meaning; their Product Owner fixes commit only the product document. Newly declared terms wait for the Architect's later `D: term-mappings` fix in `scen check`, never in refinement. The evaluator saves the raw model answer separately and saves the derived canonical verdict as response/result JSON. Fix templates branch first on `Judgement`, then retain the legacy branches verbatim; proposals carry the whole Item and `**Actual:**` for coverage attribution. Refinement commits product working copies for concept confirmations and reads a Story body for rewrites; Scenario fixes commit the architecture and needed Public interface copies as well.
