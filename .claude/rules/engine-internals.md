# Engine Internals

## build steps / build tests / build code, in depth

- `build tests` — deterministic Registry codegen: requires each suite's Steps package, naming `build steps --fix` when it is missing, then renders one `func Test<Key>` per Scenario and the tests' `main_test.go` in one pass. `main_test.go` holds `TestMain`, the suite and `New(t, id)`; tests call New directly, with no intermediate package. Plain suites use bddgo; `testing.testkit` selects `testkit.NewSuite`. The generated marker is ``// Code generated by `true-bdd build tests`. DO NOT EDIT.`` for tests and their main file. Marked files refresh, including a broken marked main; unmarked main files are preserved. `--fix` writes stale files and removes only marked legacy intermediate files; without it regenerate-and-compare refuses stale files. `scenariogen.CheckFolder` requires each Scenario's one generated test in its Registry path, no test naming a missing Scenario and every fixture tree named by a Scenario. Hidden Go staging files are ignored. The template-copy and fixture-comment contracts stay in the repository's fixture gate, and its generated-suite gate shells out to the built engine's `build tests` without `--fix`. Registry, path, renderer and step-shape refusals precede rendering. It reads no product document or definition bodies, runs no AI, offers no fix menu and starts no test runner.
- `build steps` — scans definitions before grouping distinct unbound texts per suite and block, excluding `judge:` and `llm:`. The grouping protocol reads best and runner-up scores and uses the link threshold and ambiguity rule. `config.grouping_batch_texts` defaults to 800; larger blocks use the fewest balanced batches. Missing, repeated or unknown indexes, invalid rankings and output caps crash. Every grouped or resumed concept is an Item with an unambiguous service binding before any skeleton. `judgeConceptBindings` starts a walk, shares each Item's steps and asks `scen check`'s bindings Prompt once per binding, through the same evaluator path (ADR-0037). Missing or ambiguous bindings stop. Grouping, its batch size and the bindings Prompt are loaded before grouping; malformed term lists and invalid registered patterns refuse before any AI turn. A host declaring no concepts groups nothing and its gaps remain Step coverage's findings.
  `prepareConcepts` creates and describes Items and prepares evidence and grants; it neither proposes patterns nor writes skeletons. Pending `//truebdd:concept` skeletons resume under their concept; their suite steps carry that Item's ownership. The checklist walks `pattern-bindings`, `step-coverage`, then `step-verification` in written order. `pattern-bindings` calls `catalogue.CheckPatterns` over the Item's registered patterns and every deterministic suite step. Compile errors, capture counts, foreign bindings, unused patterns and zero or multiple bindings of an owned step are findings. Fresh Items fail. Resumed registrations recover capture cardinality from their regex without fabricating proposal names; fresh proposals keep their named captures.
  The pattern item's F scalar is the former `concept-patterns` Q.prompt byte for byte. `patternProposalPrompt` adapts that F to the existing proposal protocol; no separate proposal Q remains. `generatePatternFix` proposes once with the code Q's findings and Previous patterns, preparing a candidate without edits. Refinement retains that candidate and the person's feedback. After the menu's apply choice, `applyPatternFix` calls `rewriteSkeletons`: dropped patterns go through `stepskeleton.RemoveConcept`, retained ones keep their bodies and new ones start pending. The F judges nothing; `CheckPatterns` is absent from proposal evaluation. The same code Q reruns after apply, then the checklist restarts. The walk's `max_apply_attempts` bounds applies and its named exhaustion error includes the Checklist item and concept; there is no private proposal retry loop. Bare runs answer the code Q per Item, save findings and run no F, leaving registrations unchanged.
  Step coverage's F writes the selected bodies, imports, State and helpers/. Writer grants cover only Steps packages and host tmp, with suite and Specification evidence readable. Skeleton rewrites ensure `*testkit.ScenarioRun` when declared by the architecture. Each completed body apply retains compilation, source shape, one binding per owned step, concept records and no pending sentinel checks. An `interface_cannot_serve: {concept, lacks}` stops distinctly. A walk applying any fix walks every Item again even when whole-suite coverage already passes; no test or main file is required, and no test listing or test execution occurs. BUILD STEPS COMPLETE follows convergence.
  Body proposal and apply turns embed the semantic core, complete declared `step_arguments` and bound steps; Registry, Scenario keys and fixture directories travel by path, with no fixture digest or compaction. Saved complete runtime `go doc -all` files are readable by path; runtime source remains withheld. The tool-less step-verification Q selects complete referenced source declarations and transitive State/helpers dependencies, registrations and imports, semantic core, complete declared `step_arguments`, binding-referenced Public interface entries and dependencies, and referenced runtime API declarations with required types and fields. Every distinct step form has up to three complete original examples and capture tuples; finite alternatives remain literal. No fixture files or Scenario corpus enter that Q. Every dispatch measures actual UTF-8 prompt bytes against `engine.max_prompt_bytes` (default 150000), logs both counts and refuses oversized evidence distinctly.
  `answerVerification` saves the typed answer at the Cell artifact stem. Its one F selects reported bodies through `fixSubject`; pattern findings call the same proposal protocol with Previous and Critique, then `beforeApply` uses the same `rewriteSkeletons` before the selected body writer. It makes no pattern check. The verification Q runs immediately after apply; once it passes, the checklist restarts and the code Q judges the changed patterns. The trace test deliberately has verification's F propose a pattern that code refuses. A later coverage F restores whole-Item body scope. The five categories diagnose one question, and every F fixes only its Q's findings. Verification retains ordinary tier precedence and the historical `build_steps_critique` template keys. Grouping, the binding judgement and structural checks after apply remain outside the checklist for their own tickets.
- `build code` — before its first discovery and any AI turn, Go suites with a Steps package run `checkCodeRed` when a service has no source. `architecture.Service.HasCode` inspects only regular files under that service's path and writable paths, using Go `.go`, TypeScript `.ts`/`.tsx`, JavaScript `.js`/`.jsx`/`.mjs`/`.cjs`, or any regular file for an unlisted language. Manifests alone do not count for the listed languages. It lists every generated Scenario test, then runs the suite once and requires each Scenario of a service without code to fail at an executed definition. A green Scenario stops with `ErrScenarioGreen`, naming it, without a fix path. An unreadable or malformed configured Registry stops this preflight with `ErrRedCheck`, naming the document. Compilation, bring-up, skipped or missing results are `ErrRedCheck`. Existing source skips this check; Jest and Playwright retain their behavior. After this preflight it starts every outer walk with full discovery through `testing.commands.replay`, yielding zero Items or one whole failing set (`commands.BuildCodeItem`). Its `tests-pass` built-in code Q answers through `runner/check_cell.go`, without a validation turn; all latest member verdicts must pass. The fix turn proposes one plan naming changes, files and served tests. The apply turn is the writer: it gets the same set, the linked concepts and their words, all matched Scenarios and steps, Specification paths, declared service edit roots, and codex and Claude whole/selected replay forms. It reads the Specification and harness, implements the service, tests each part and every set member, and reports changes and observed passes. No prompt budget is stated. Every completed apply (including `applied: false` and the terminal attempt) reruns the remaining set in `PostFix`/`PostNotApplied`, in one framework runner start. A successful provider response missing the result block (`ErrFixApplierNoContent`) follows `PostNotApplied` only for `build code`, keeps files and logs one WARN carrying the result path. Started codex non-zero/empty outcomes and Claude non-zero/error-result/empty outcomes also preserve files, warn once and follow PostNotApplied. Start failures, engine refusals before spawning, other commands and roles retain fatal handling; malformed extracted blocks and missing `applied` retain their existing handling in every command. The writer ends its final message with the confirmation block in the message itself; the engine saves the block at its heading's path, which the writer never writes. Selectors are joined by alternation; Go `<build>` or Playwright `<startup>` makes the rerun unfiltered. Members need their own passing result; missing/skipped results stay failing with a did-not-run finding. Passing members leave; grouped evidence uses build-tests runtime normalization but retains the whole first output and every member id. `BeforeEvaluate` leaves the verdict to the code Q. The per-Checklist-item allowance permits at most max_apply_attempts applies; membership changes never reset the same Item's counter. Every apply is rechecked by its own Q. A failed recheck after the last allowed apply stops with FIX_LOOP_NOT_CONVERGING before another F; a passing recheck restarts the checklist. The outer walk bound remains separate. Fresh outer discovery catches previously green regressions. Exit ends the Item. For ordinary failure enrichment, optional Specification documents warn and are omitted when unavailable; exact module-aware Go identities alone match Registry Scenarios. `codeConceptSpecifications` (`build_code_concepts.go`) gives each matched Scenario the concepts its deterministic steps link to: the `//truebdd:concept` record (`stepskeleton.Concepts`, by registered pattern) of the one definition `stepcoverage.LoadSuite` binds the step to, naming a declared concept of its block, with that concept's bindings for the Scenario's service; `catalogue.SpecifyConcepts` adds its terms' glossary entries and Word mappings and `BuildCodeItem.Specification` unions concepts by block and name, joining bindings by service. Both build-code fix templates render them under `{{ if .Concepts }}`, nothing for a host declaring no concepts (`TestBuildCodeTurnsEmbedTheLinkedConcepts`); fixtures extending those templates carry the same prefix. The mandatory `testing.commands: {record,replay,live}` block has no built-in defaults; record accepts a command string or `{command: string, exclude: [pattern, ...]}`, retaining the command string for every command reader and refusing malformed forms distinctly; replay and live remain strings; native machine-output flags and config-directory cwd are retained by engine runners. Static refusals precede subprocesses; spawn-only errors report `Cannot run test suite` / `Cannot run suite` as `runner.Reported`. Build-code write roots are the failing set's service paths and exact `writable` entries, plus host tmp; unknown-service failures use all services. Existing folders grant their subtree; absent writable entries remain exact leaves unless a trailing slash declares a folder. Before discovery (and before evaluating the remaining set), the engine refuses outside or parent-traversing paths, patterns and overlap with protected tests: `tests/`, Registry suite directories, the in-host `testing.config` directory and named Go command package directories (`./dir` or `./dir/...`, relative to the runner cwd), step definitions included. Broad `./...` names no separate test directory. Command package directories inside a service path, including its `_test.go` files, stay writable service code; reserved tests, Registry and config directories take precedence. The plan's build-code-only schema and the writer's confirmation carry `impossible: [{path, reason}]`: only a truly impossible repair qualifies, after seeking a permitted solution. A nonempty verdict retains edits, reruns the remaining set once and returns `ErrImpossibleWork` with files, reasons, remaining failures and the manual-or-writable remedy, through the walk's error path before any COMPLETE banner. An empty list preserves ordinary retries. Document commands still reject `applied: false` before their commit hooks.

**Glossary form (#287):** every product reader and `product.ValidateForm` refuses a glossary `means` outside one paragraph, three sentences or 25 words per sentence, naming the term and observed counts. Sentence terminals are runs of `.`, `!`, `?` followed by Unicode whitespace or EOF, with a remaining fragment counted; words are Unicode-whitespace-separated fields. Blank lines separate paragraphs. Concepts’ `means` are unchanged. `glossary-form-001-startup-refused` pins zero-turn startup refusal; legacy malformed-document findings remain with their commands. The architecture schema makes `observed_by` optional when the binding already fixes observation.

**Startup refusals**: every command reports precondition failures as `Cannot start: …` on stdout plus a `Refusing to start` slog record. The container refuses a host still declaring the template form, naming its replacement (the Owner's decision, 30 October): `product.ValidateForm` a product document with a `catalogue` key, even empty or null (`ErrCatalogueRetired`), or a concept holding a key beyond `concept`, `means` and `terms`, naming block, concept and key before `node.Decode` drops it (`ErrUndeclaredConceptKey`, #268, `concepts-009`; every `product.Load` reader refuses it too), and `architecture.ValidateForm` one with `architecture.phrases` (`ErrPhrasesRetired`); an unreadable document stays the command's finding (`engine-term-documents-003`). `product.Load` and `architecture.Load` refuse them too, as a fix writing one back does (`concepts-002`, `concepts-006`) — the BDD judge reads the log, not the terminal, and `stdout_regex` matches stdout alone. All go through `runner.RefuseStartup`, a container `cmd` cannot build among them (`containerFor`), except two whose messages Scenarios pin: the `docs:` check (`Refusing to start: checklist documents unsatisfiable`, inline in `validateSpec`) and a document key `cmd` cannot resolve (`Refusing to start: document unresolvable`, `refuseUnresolvedDoc`). An error already diagnosed by the code that produced it is wrapped in `runner.Reported` so it is not announced twice. A walk that stops mid-way (a Checklist item still failing after `config.max_apply_attempts` applies, a failed AI turn, a check that cannot answer) is logged once more by `runner.Run` as `level=ERROR msg="Walk stopped"` with the command and the error, since cobra prints the error only to stderr (`fix-loop-bounds-002`).

## Model tiers and providers

The engine drives two agent CLIs — `claude`, `codex` — picked per checklist role. `engine.models` binds tiers (`xhigh`, `high`, `coder`, `quick`) to `"<cli>:<model>"` (split on the FIRST colon only); `engine.default_prompt_model` / `default_fix_model` / `default_apply_model` name each role's fallback tier. Per-cell resolution: prompt override (`model:`/`fix_model:`/`apply_model:`) → checklist `engine:` block → `engine.default_<role>_model`. Anything unresolvable is a startup error, never a silent substitution.

- **Turn lifetime (ADR-0025):** the router adds no deadline to any role or CLI. Every turn runs with the caller's context; cancellation stops its process group and descendants and remains fatal. No time, turn, token or cost budget is added to requests, prompts, checklists or templates.
- `internal/domain/models/provider/` owns the vocabulary (`ModelRef`, `Tier`, `Registry`); the registry is validated once in `bootstrap.newAIRouter`. `adapters/ai/router.go` is the only `ports.AIPort` implementation.
- `ExecutionMode.WriteGlobs()` supplies the write patterns for Claude's guard and codex's apply profile; `AllowsBash()` also guides Claude tooling. The router independently selects codex apply confinement by role, leaving plan and validation read-only.
- The fix generator and applier never see the prompt; the evaluator resolves their tiers and carries them on `ValidationResult.FixModelTier`/`ApplyModelTier`.
- **Claude build-code writer (2.1.285, ADR-0022):** only this applier requests `TurnOptions.ClaudeWriter`. The wrapper uses generated `--settings`, `--restricted`, an explicit six-tool inventory (MultiEdit is named but absent in 2.1.285), default permission mode and no safe mode. `claude-guard --policy <generated JSON>` receives every PreToolUse payload and explicitly grants only canonical foreground Bash or confined file tools. Bash has no permission allow pattern; both Bash timeouts are 600000 ms. Read roots are the host, GOROOT, the architecture-declared library graph and its exact version metadata, and this session UUID's tool-results directory. A module cache inside the host stays restricted to that graph. The generated policy and library-download scratch are protected from writes. Claude's replay remains unconfined with network for model trials (ADR-0028, Q15). Searches outside the host reject ancestors of excluded module copies; Glob also checks its fixed pattern root and denies parent traversal. Writes derive from the execution mode's roots, excluding the generated settings/policy directory. User/project CLAUDE.md, automatic memory, skills, installed plugins, commands, workflows and MCP stay disabled. Default sign-in is retained because an empty config dir was signed out. The applier renders Claude foreground completion or codex native polling directly from the shipped template. Started Claude non-zero exits, error results and empty replies carry `errors.ClaudeTurnError`; only the build-code applier recovers them, with one WARN and `PostNotApplied`. Stream cost survives failed results. Start failures remain fatal. Other Claude turns retain their arguments and share the unbounded, cancellable lifetime.
- **codex applies (0.162.1, ADR-0021 and ADR-0024):** the router sets `Request.CodexApply` for every codex apply role regardless of command or tools. `TurnOptions.CodexWriter` remains build-code-only and selects replay forms and recovery. Generated per-turn `CODEX_HOME` copies only private `auth.json`; its profile denies commands access to the shared host tmp/codex-homes subtree for all turns and runs; auth.json is removed on preparation or turn completion, success or failure, and cleanup errors are reported. The profile denies every filesystem path outside the host except `:minimal` OS runtime, GOROOT, the architecture-declared library graph and exact version metadata, and the explicit runtime grants below. The module cache is denied by default with narrower library read entries; its cache/vcs subtree, protected library-download scratch, and implicit `/private/tmp`/`/private/var/tmp` scratch are denied; host roots take precedence where nested. The mode's file, directory and configured-glob roots and host tmp are writable. Existing files stay files; literal directory roots and file parents use rooted creation. Configured globs allow matching new files even without existing matches. Terminal `/**` retains its literal subtree grant; other wildcards grant the narrowest literal directory and enforce the original patterns after every turn. Newly created non-matching files are removed; a pre-existing non-matching file changed, deleted, renamed or given different permissions fails the turn with one WARN naming it. Overlapping grants authorize their union; these violations are fatal even for build code. Generated homes are excluded from comparison; malformed patterns, host-root grants and escapes refuse (ADR-0024). Source-root symlinks escaping the host are refused. Command environment inherits nothing: controlled PATH, HOME/TMPDIR/GOCACHE under host tmp, TMPPREFIX at host tmp/codex-tmp/zsh for zsh here-documents, Go roots, offline proxy/sumdb, local toolchain, disabled telemetry/CGO and `-trimpath -buildvcs=false`. Before the turn, the engine creates private codex-shell-home, codex-tmp and codex-go-build directories inside host tmp. Optional installed node/npm/npx/docker binaries, npm's validated package, Mach-O dependencies and their installation symlinks are explicit read grants; Homebrew opt directories permit link metadata, with unrelated canonical targets denied. npm/npx JavaScript package roots require package.json naming npm and resolved bin/npm-cli.js or bin/npx-cli.js, outside the host, authentication and sensitive home roots enumerated in ADR-0024; otherwise the runtime is refused with a WARN and no link or grant. Generated runtime-bin links, offline npm cache/config, Docker config and all writable runtime state stay in scratch. No Docker daemon or socket is granted; `OPENSSL_CONF=/dev/null` avoids outside OpenSSL configuration. No outer sandbox. Generated config suppresses user config/MCP/web/history/AGENTS.md/host skills/plugins/apps; high reasoning, configured window 1050000 (1M unverified). `--json` stdout is archived separately from stderr; `-o` remains the answer. Drill audit reads commands and file changes without inferring read success. Started non-zero/empty/missing-answer outcomes carry `CodexTurnError`; build code alone preserves edits, warns once and reruns `PostNotApplied`. Start failures stay fatal. No codex stall watch. Planning and validation keep argv, environment and read-only sandbox; other commands' confined applies retain fatal failures. Cassette filtering excludes generated homes and shell/build scratch.
- **Answer schemas (#299 recording refusals):** Claude passes `--json-schema` as a tool input schema and refuses top-level `oneOf`, `anyOf` or `allOf` (HTTP 400 `tools.5.custom.input_schema`). Both providers require `additionalProperties: false` on every object. Codex strict output refuses missing object closure (`invalid_json_schema`, `text.format.schema`, observed at `anyOf/0`) and requires every property in `required`; optional properties become nullable, including their enum when present. An empty object's `required` remains `[]`, never null. Answer schemas use no string length, numerical, recursive reference or complex array constraints (`minItems`, `maxItems`, `uniqueItems`, `contains` and their bounds). Semantic checks belong after parsing: a non-null `cannot_fix` excludes ordinary work and needs a nonblank reason and correction; an invalid or mixed answer returns `ErrCannotFixMalformed`, distinct from `ErrCannotFix`. `TestAnswerSchemasAcceptedByProviders` walks every answer schema through the actual adapters with local CLI stand-ins, inspecting Claude's schema argument and Codex's schema file. Apply and writer turns use result blocks without schemas; clarification replies reuse the proposal schema.
- **codex gotchas (verified live, codex-cli 0.162.1, #165):** `--output-schema` refuses a schema whose `required` leaves out any property, which claude accepts, so `CodexProvider` lists every property there before writing the schema file. codex writes its own answer file, so the cassette carries it: it is `-codex-answer.txt`, since a `.md` there fails alint's `text-final-newline` (codex ends its message with no newline).

## Prompt data contract

Checklist Models are declared on the service in `architecture.services[].models`: four paired entries name templates and fields/types-only YAML JSON Schemes. Construction rules belong in short Scenarios naming the Model. The engine checks an explicit YAML view of actual call inputs and Subject before rendering, preserving typed data and every prompt byte. Schemes resolve from `templates.schemes.<model>`, defaulting to `true-bdd/models/<model>.schema.yaml`, like template paths; init ships them, runtime never falls back. Before its walk, `scen check` checks declared resources and Scenario references. Other roles remain in `architecture.prompt_data`; preserve their anchor values and update their prose with any transformation change. Shared byte rules stay in `model_rendering`, concept protocols in `concept_protocols`.

## Build identity

`version` is a plain terminal answer: exactly `true-bdd version <version> commit <commit>` and a newline, without loading configuration, installing logging or creating files or directories. Commands that install the engine log, including `init`, emit one INFO `Engine started` record with `version` and `commit` before any other record. `engine-entry-005-version-reports-build` pins the file-free answer; `build-tests-files-002-stale-test-regenerated` pins the start record without an AI turn.

## Package notes

- The engine owns all code it uses from this repository: `internal/infrastructure/{console,disk,logging,shell,enginelog}` are its IO channels and log vocabulary; `internal/infrastructure/cli/` exposes the spawn vocabulary and typed wrappers `claude`, `codex`, `git` (environment scrubbing), `gotool`, `spec` and `truebdd`. Only the shell imports `os/exec`; only those explicitly named wrappers import the shell. Logs use the engine's logging channel, files its disk channel and terminal descriptors its console channel. The domain imports none of these implementations. `pkg/` remains independent code for tests and tooling and the engine never imports it. The `Engine owns repository code` gate scans all engine Go imports, including tests and hidden build variants; the drill records its result in `engine_imports`. CLI argv/stdin remain the byte contract stated in `docs/architecture/architecture.yaml` (`dependencies[].invocation`); change an invocation and that statement together.
- `internal/app/generators/scenariogen/` renders registry → Go test. `BuildPlan` refuses the whole registry before writing a byte; `Render` always runs `format.Source`; `Write` refuses a target without the generated marker. Its template is `//go:embed`ed (it must compile against bddgo's API), not under `templates/`.
- `internal/infrastructure/stepcoverage/` parses each suite's `steps/` package and resolves which registry steps bind to nothing. Its mirror of bddgo's resolver is checked by running both: with the suites green, engine and runtime must agree on every scenario.
- `internal/app/checks/` holds Built-in checks named by `Q.code` (ADR-0042). A command's `runner.Spec.Checks` is its `checks.Set`; `runner/check_cell.go` answers these Cells without the evaluator, saving the same verdict artifacts. Q is a mapping with exactly one `prompt` or `code`, parameters stay under `with`, and `validation_prompts` keeps its name. Legacy D, scalar Q, both, neither and extra option keys refuse at start, including parked malformed entries; `model:` refuses on a code Q. `PromptWithContext.Index` is the selected written file position, used for both walk and artifacts. The runner does no reordering and no failed-code skip. Both walkers pause a fixable failure before later Qs, apply its F, recheck that Q until pass or the existing bound, then restart its Item; an outer walk that applied a fix walks all Items again. Concurrent Items validate independently, menus are in Item order, and bindings retain their all-links barrier. `BeforeRecheck` invalidates shared verdicts while retaining linked steps for the immediate Q; `OnValidate` starts the full fresh walk. A check's `Docs` must list every document it reads, or startup refuses.
- The closure checks `declared-terms`, `term-mappings`, `concept-bindings` and `step-definitions`, with `public-interface` (#239) beside them in `internal/app/checks`: `internal/infrastructure/product` reads the product document's `concepts:` and `glossary:`, the only parts the engine decodes, and refuses the retired `catalogue` key and any concept key beyond `concept`, `means` and `terms`; `internal/domain/models/catalogue` keeps the step vocabulary as data (blocks, `catalogue.Step`s of `RegistryScenario.CheckedSteps`, concept specs, term reviews and the pattern check). All four closure checks share `checks.closureCheck`: a product declaring no `concepts:` passes every Scenario as "not checked: the product document declares no concepts"; otherwise every Scenario is checked, a Story claiming it or not. `declared-terms` and `term-mappings` hold every declared concept's `terms` to the glossary and to the architecture's `terms:` (`architecture.LoadTermMappings`, `catalogue.ReviewTerms`/`ReviewMappings`), each finding naming its concept once (`then concept 'answer' declares "reply", which the glossary does not define`, pinned by `scen-check-fix-002`). `concept-bindings` holds every `architecture.concepts` binding to a declared concept, one binding per concept, block and service, and references its service's Public interface declares, or a UI service's intent. `step-definitions` is `reviewConceptDefinitions`: each non-model step of the Scenario binds one definition whose `//truebdd:concept` record (`stepskeleton.Concepts`, matched by registered pattern) names a concept the product declares under the step's block; two bindings, no record, another block's or an undeclared concept fail, and a step no definition binds yet passes, listed as `N steps unbound yet`, since `scen check` runs before `build steps` writes it (ADR-0037). A check's error stops the walk and is logged as `msg="Check could not answer"`, since cobra prints it only to stderr. `scen check --fix` writes a closure fix to the term documents, the product and the architecture document, and a model Prompt's fix to the product document or the Scenario's own Registry entry: `commands/fix_documents.go` seeds `tmp/<run>/<key>.yaml` per term document the host has and one for the Registry, the applier edits that copy in EditMode (codex apply confinement grants the mode's scratch writes; an existing single-file source root stays a file), and `PostFix` puts a changed copy over the document once it parses and its concepts and glossary, its word mapping, or its Scenarios (the same ids) load, every changed copy checked before any is committed (`commitScenarioFix`, interface copies first). A copy that does not read as its document (`ErrTermDocumentUnparseable`) is a fix not taken, in `us refine` too (#268): `fixNotTaken` resets every copy of that fix to its document and wraps the refusal in `runner.ErrFixNotTaken`, which `runner.commitApplied` logs as WARN `Fix not committed`, keeping the Item; the walk restarts, the same Item and Prompt's next failed result carries the refusal as its last `Context` line (`fixRefusals`), and the walker's per-Prompt fix bound counts it (`concept-link-021`); a `public-interface` or `concept-bindings` fix commits the architecture and the interface documents through `commitInterfaceFix`, which refuses a copy declaring `architecture.phrases`. A changed Registry is reloaded into every walked Item in place, so the restarted walk asks about the Scenario as it now reads. A fix stands only once a walk converges: a run that ends otherwise (out of walks, the exit choice, a walk that stopped) puts every document it wrote back as it read before the walk (`commands.fixLedger`, `fix-loop-bounds-004`). Its fix-generator template renders `FailedCheck.Context`, the only place a Q.code finding reaches the model; the other commands' templates do not. Each scen-check fix template chooses its wording by the failed result: a concept judgement (`Judgement`), then `public-interface`, then a model `Q:` Prompt (`eq .FailedCheck.Check ""`, the applier's `eq .Check ""`) with the Scenario-rewriting text and the Registry's working copy, else the concept document text naming the glossary for `declared-terms`, the word mapping for `term-mappings` and `architecture.concepts` for `concept-bindings`. The closure applier templates name `architecture.terms:` only when `.Subject.Writes "architecture_yaml"`. `us refine` walks a `template.StoryRefineData` (the Story embedded, so its templates read the Story's fields unchanged) and holds no built-in check: its `Spec.Checks` is empty, and its concept judgements' fixes seed the term documents' working copies as `scen check` does, its applier running in EditMode, `refinePostFix` committing a product working copy for a concept confirmation and reading a Story body for a rewrite. It reads the confirmation as `checkFixApplied` does (`validate.IsConfirmation`): a block an unquoted `:` keeps from decoding still commits when an `applied:` line says so, and content with neither is parsed as a Story body, failing as one (#267, `concept-link-020`). Its four `us-checklist.fix-*` templates branch only on a concept judgement, the `Q:` text otherwise.
- `internal/infrastructure/architecture/loader.go` decodes ONLY `testing:` (`framework`, `config`, `commands`, `libraries`, `testkit: {repo_layer: [...], fixture_step: ...}`), each service's `name`/`path`/`language`/`writable`/`libraries`/`public_interface`/`models` and `concepts:`; it refuses the retired `architecture.phrases` (`ErrPhrasesRetired`), while `term_mappings_loader.go` reads `terms:` and `concept_bindings_loader.go` `concepts:` with duplicates kept. Each service's third-party CLI `dependencies` and their `recording` rules, plus `testing.commands.record.exclude`, are copied to the tests' main file. `pkg/testkit` adds the host-relative exclusion patterns to every dependency's `unread`; a plain-string record command supplies none. Other sections under `architecture:` stay undecoded — only `go run ./scripts/cmd/linters schemas` would notice a typo there.
- **A new checklist costs a fixture run per branch.** `scripts/cmd/coverage` requires the checked-in `baseline.yaml` to cover EVERY (prompt × pass/fail) branch of every shipped checklist (`assertBaselineComplete`), and `TestUniverseCensus` pins the Q/F/branch counts — so an 8-prompt checklist needs one fixture scenario designed to pass all 8 and one designed to fail all 8. The walk continues past a failure when no `F:` exists (`CellFailedNoFix` → `idx++`), which is what lets one run cover eight branches. A prompt with an `F:` has a third, `fix`, branch, which only a `--fix` run that fails the prompt, applies the fix and converges covers: the `scen-check` quality and model closure prompts get one recorded fixture each, narrowed to that prompt by `checklist-prompts.yaml` (one per pinned prompt in `declaredSelections`). A fixture's own checklist credits a shipped prompt when its question or check, rationale, `F:` and docs are the shipped ones verbatim (`EvalKey`), which is how `scen-check-fix-002` to `-004`, `public-interface-fix` and `concepts-fix-operation` cover the five closure checks' fix branches: copy a shipped prompt into a fixture's checklist byte for byte. Regenerate after a full replay: `go run github.com/ondatra-ai/true-bdd/scripts/cmd/coverage -session <s> -write-baseline`. `Baseline.Write` is fail-closed on HARD diagnostics and `-rebaseline` does NOT lift that; eight fixtures (`build-code-command-not-executable`, `build-code-jest-no-tests`, `us-apply-{malformed-scenarios,missing-story,shared-prefix,story-id-mismatch,story-without-acs,unshaped-criterion-id}`) emit one every session, so delete their run dirs from the scanned session first — they contribute no coverage, having no AI turns.
- `true-bdd/*-schema.yaml` are host document-lint contracts, enforced by `go run ./scripts/cmd/linters schemas`. Pairing uses the whole document key, underscores included (`architecture_yaml-schema.yaml`); a schema naming no configured document fails the gate. `true-bdd/models/*.schema.yaml` instead hold checklist Model contracts, read and checked by the engine in process.

## Run-only model overrides

Every AI-turn command (`us refine`, `us apply`, `scen check`, `build steps`, `build code`) declares repeatable `--model <tier>=<cli>:<model>` flags. Lazy bootstrap validates the loaded tier table and role defaults first, then validates all overrides against declared tiers using the config's model-reference parser; duplicate tiers, undeclared tiers and invalid references refuse startup with exit 1 before any turn. The resulting in-memory registry changes only the named tiers, preserving Prompt → checklist → role-default selection. Each override logs once at INFO with `msg="Model tier overridden"`, `tier`, `from`, `to`. Apart from logs no override is written to a file, and none enters a spawned process's environment; the resolved model travels as its CLI argument. The drill accepts only repeated `--model` value pairs after `build steps --fix` or `build code --fix`, and none after `build tests --fix`; it keeps them in the run's argument record and forwards values unchanged through typed wrapper options. Engine startup owns semantic validation; deterministic `build tests` has no `--model` flag.

**Concept judgements (#257):** `with.concepts` selects link, group, bindings, sketch or words on a Q Prompt. A host declaring no concepts omits link/group/binding/word cells and gets Prompt 12's plain text. Concept links are current-walk Item evidence, never Registry data. Word judgements require that walk's successful link and a complete verdict for every linked meaning; their Product Owner fixes commit only the product document. **Shared judgements (#264):** `scen check` sets `runner.Spec.ShareConceptJudgements`, so it always walks with the concurrent walker, at concurrency 1 too: `ConcurrentWalker.Waits` holds the bindings Prompt (`judgesBindings`) until every item has answered every Prompt before it, and `OnValidate` calls `ChecklistEvaluator.StartWalk` at each validation round, `--fix` rounds included, so no verdict outlives a round. In a started walk a `*template.ScenarioCheckData` cell answers from `validate.conceptSharing`: each binding (block:concept@service) and each linked concept's words is one turn, claimed by the first cell needing it; a cell judges every key no cell has claimed before it waits for another's turn, so none waits holding a claim. A passing link publishes its linked steps (`finishLink`), and a binding turn reads every distinct one reaching its concept for the service (`stepsLinking`), the product, that binding and means, and the Public interface; a words turn reads the product and that concept. Each Scenario's cell grades its keys' answers into today's context lines. A shared turn saves `NN-shared-NN-<judgement>-<key>-…` artifacts, takes the `validation-NN-<sha256(key)>` label above concurrency 1, and logs `Shared concept judgement answered` with `promptIndex`, `judgement`, `concept`, `service` and `askedBy` (`scen-check-speed-003`). `build steps` starts a walk of its own before its binding judgements, so a binding outside a started walk is an error (`errBindingsOutsideWalk`); outside one only `us refine` keeps its per-Item turn, one Story's words in one. Newly declared terms wait for the Architect's later `Q: {code: term-mappings}` fix in `scen check`, never in refinement. The evaluator saves the raw model answer separately and saves the derived canonical verdict as response/result JSON. Fix templates branch first on `Judgement`, then on the failed check; proposals carry the whole Item and `**Actual:**` for coverage attribution. Refinement commits product working copies for concept confirmations and reads a Story body for rewrites; Scenario fixes commit the architecture and needed Public interface copies as well.

## Cannot-fix outcomes

Any F can return the optional `cannot_fix` mapping, with `reason` and `correction`, at proposal, after clarification or at apply. An F fixes only what its Q found; it receives the question, answer, context lines and item's F text. A problem its Q did not find is neither its work nor a reason for cannot-fix. A person who has not decided is a legitimate cannot-fix. The run stops with its reason and what a person must correct, without asking for an Earlier step (a previous command of `us refine`, `us apply`, `build steps`, `build tests`, `build code`). Structured proposals advertise it only in the answer schema; other proposals and writers receive the shared instruction. `runner.locateCannotFix` adds the Checklist item's section and index while preserving error identity. `interface_cannot_serve` and `impossible` remain instances with their wire shapes and logs; build-code plan and apply still rerun the remaining set once before stopping. This protocol changes F request hashes: inventory affected fixtures and cost before the Owner authorizes recording.
