# Engine Internals

## build tests / build steps / build code, in depth

- `build tests` — deterministic Registry codegen only: one `func Test<Key>` per Scenario into its `path:`. `--fix` writes stale files; without it regenerate-and-compare refuses stale files. Registry, path, renderer and step-shape refusals precede rendering; steps are free text, matched against nothing. It does not read the product document or step definitions, run AI, offer a fix menu or start a test runner.
- `build steps` — scans definitions before grouping the deduplicated unbound texts per suite and block, excluding `judge:` and `llm:`. The `Q:` group protocol takes the best and runner-up scores and reuses the link threshold selector and ambiguity verdict. Its checklist `config.grouping_batch_texts` defaults to 800, measured for `claude-opus-5` and this answer format; the engine divides larger blocks into the fewest balanced batches. Missing, repeated or unknown indexes, invalid rankings and output-cap errors crash. Semantic link failures name every step and ambiguous concepts before any skeleton. Each concept and suite is an Item; every grouped concept must have a binding for the service, rejudged using `scen check`'s exact binding Prompt and evaluator. Missing or ambiguous bindings name the concept and stop. A host declaring no concepts groups nothing (`conceptSuites`): it has no Item and its unbound steps stay Step coverage's findings. A bare run then lists the Items (`ErrMissingStepDefinitions`, or COMPLETE with none) and answers `D: step-coverage`. `--fix` runs the grouping, bindings and proposals inside `runner.Spec.LoadItems` (`prepareConcepts`), with `OmitConceptJudgements` so the walk answers only `D: step-coverage`; it first reads the propose Prompt, the product's concepts and glossary, the Word mapping and the bindings (`loadConceptRun`), so a malformed term list is refused before any turn (`engine-term-documents-005`, `-006`). Resumed Items come from `stepskeleton.Concepts`: a step whose one definition is a pending `//truebdd:concept` skeleton belongs to that concept's Item, gets its binding rejudged, and is never grouped or proposed again. The `Q:` propose protocol (`validate/concept_propose.go`) sends the concept, glossary entries, binding, Public interface, the concept's existing patterns and the grouped steps, plus the refused patterns and findings on a resend; a malformed answer crashes. `catalogue.CheckPatterns` decides from the proposal alone, per Item, against every deterministic suite step in every block: a pattern binds only its Item's grouped steps, each of those exactly one pattern, and every pattern some step; compile and capture-count errors refuse too. Up to `max_apply_attempts` proposals, then `ErrPatternProposal` before any skeleton. `stepskeleton.WriteConcept` names a skeleton from block, concept, suite and pattern. `--fix` uses `runner.Spec` and the shared Fix loop: preflight term lists, Public interfaces, the bindings and architecture-derived protected test grants; write every skeleton and compile before AI. Writers change only the selected bodies, imports and shared State. Each completed apply checks source shape across all the Item's functions, suite compilation, that each step binds exactly one of the Item's definitions, that the concept record survives and no pending sentinel; failed findings return to the same Item. A nonempty `interface_cannot_serve: {concept, lacks}` confirmation, `concept` the Item's label (`when concept "halving"`), stops immediately with a distinct architectural error naming both. Convergence runs whole-suite Step coverage, package-qualified generated-test listing and one suite run in a Host project copy without every service path, VCS metadata or scratch. Each Scenario must fail at an executed definition (the harness's numbered step failure diagnostic). Compilation, bring-up, skipped or missing results are distinct failed checks naming the Scenario. A green Scenario returns all Items written in this run whose steps it uses together, with the finding, through runner.Spec.CheckConvergence and the engine's bounded outer walk. Per-Item apply counts persist across these checks; a green Scenario without a written Item stops distinctly. BUILD STEPS COMPLETE follows only a successful red check. The pipeline is `us refine`, `us apply`, `build tests`, `build steps`, `build code`. The concept context (`build_steps_concept_context.go`) also carries `fixture_inputs` (`conceptFixtures`): for every Scenario using the Item's steps, each `<suite>/fixtures/<name>/` a quoted step value names, every file but `cassettes/`, whole; it is omitted when empty, so hosts without fixtures render as before. The concept critique judges patterns too: `pattern_captures` and `pattern_scope` are against the pattern (`validate.CritiqueFinding.Pattern`), `concept_binding` (also a body requiring more than its binding and those fixture inputs), `concept_meaning` and `computes_assertion` against the body. `applyCritique` sends a pattern finding through `repairPatterns`: the propose Q again (`conceptRun` keeps the Prompt, attempts and Specification `loadConceptRun` read) with the Item's steps re-marked as its own, its patterns refused and the findings as `ConceptProposalData.Critique`, then `rewriteSkeletons` (`stepskeleton.RemoveConcept` for dropped patterns, which refuses a file holding more than the skeleton), compile, context and shape refreshed, and a pending-body finding. Body findings go back to the writer unchanged. Artifacts remain in host tmp.
- `build code` — starts every outer walk with full discovery through `testing.commands.replay`, yielding zero Items or one whole failing set (`commands.BuildCodeItem`). Its `tests-pass` built-in `D:` Prompt answers through `runner/check_cell.go`, without a validation turn; all latest member verdicts must pass. The fix turn proposes one plan naming changes, files and served tests. The apply turn is the writer: it gets the same set, the linked concepts and their words, all matched Scenarios and steps, Specification paths, declared service edit roots, and codex and Claude whole/selected replay forms. It reads the Specification and harness, implements the service, tests each part and every set member, and reports changes and observed passes. No prompt budget is stated. Every completed apply (including `applied: false` and the terminal attempt) reruns the remaining set in `PostFix`/`PostNotApplied`, in one framework runner start. A successful provider response missing the result block (`ErrFixApplierNoContent`) follows `PostNotApplied` only for `build code`, keeps files and logs one WARN carrying the result path. Started codex non-zero/empty outcomes and Claude non-zero/error-result/empty outcomes also preserve files, warn once and follow PostNotApplied. Start failures, engine refusals before spawning, other commands and roles retain fatal handling; malformed extracted blocks and missing `applied` retain their existing handling in every command. The writer ends its final message with the confirmation block in the message itself; the engine saves the block at its heading's path, which the writer never writes. Selectors are joined by alternation; Go `<build>` or Playwright `<startup>` makes the rerun unfiltered. Members need their own passing result; missing/skipped results stay failing with a did-not-run finding. Passing members leave; grouped evidence uses build-tests runtime normalization but retains the whole first output and every member id. `BeforeEvaluate` leaves the verdict to `D:`. The walker attempt counter and outer bound are unchanged: allowance two still permits three applies; membership changes never reset the same Item's counter. The terminal apply is rerun but still fails at the bound even if the rerun passed. Fresh outer discovery catches previously green regressions. Exit ends the Item. Optional Specification documents warn and are omitted when unavailable; exact module-aware Go identities alone match Registry Scenarios. `codeConceptSpecifications` (`build_code_concepts.go`) gives each matched Scenario the concepts its deterministic steps link to: the `//truebdd:concept` record (`stepskeleton.Concepts`, by registered pattern) of the one definition `stepcoverage.LoadSuite` binds the step to, naming a declared concept of its block, with that concept's bindings for the Scenario's service; `catalogue.SpecifyConcepts` adds its terms' glossary entries and Word mappings and `BuildCodeItem.Specification` unions concepts by block and name, joining bindings by service. Both build-code fix templates render them under `{{ if .Concepts }}`, nothing for a host declaring no concepts (`TestBuildCodeTurnsEmbedTheLinkedConcepts`); fixtures extending those templates carry the same prefix. The mandatory `testing.commands: {record,replay,live}` block has no built-in defaults; native machine-output flags and config-directory cwd are retained by engine runners. Static refusals precede subprocesses; spawn-only errors report `Cannot run test suite` / `Cannot run suite` as `runner.Reported`. Build-code write roots are the failing set's service paths and exact `writable` entries, plus host tmp; unknown-service failures use all services. Existing folders grant their subtree; absent writable entries remain exact leaves unless a trailing slash declares a folder. Before discovery (and before evaluating the remaining set), the engine refuses outside or parent-traversing paths, patterns and overlap with protected tests: `tests/`, Registry suite directories, the in-host `testing.config` directory and named Go command package directories (`./dir` or `./dir/...`, relative to the runner cwd), step definitions included. Broad `./...` names no separate test directory. Command package directories inside a service path, including its `_test.go` files, stay writable service code; reserved tests, Registry and config directories take precedence. The plan's build-code-only schema and the writer's confirmation carry `impossible: [{path, reason}]`: only a truly impossible repair qualifies, after seeking a permitted solution. A nonempty verdict retains edits, reruns the remaining set once and returns `ErrImpossibleWork` with files, reasons, remaining failures and the manual-or-writable remedy, through the walk's error path before any COMPLETE banner. An empty list preserves ordinary retries. Document commands still reject `applied: false` before their commit hooks.

**Startup refusals**: every command reports precondition failures as `Cannot start: …` on stdout plus a `Refusing to start` slog record. The container refuses a host still declaring the template form, naming its replacement (the Owner's decision, 30 October): `product.ValidateForm` a product document with a `catalogue` key, even empty or null (`ErrCatalogueRetired`), and `architecture.ValidateForm` one with `architecture.phrases` (`ErrPhrasesRetired`); an unreadable document stays the command's finding (`engine-term-documents-003`). `product.Load` and `architecture.Load` refuse them too, as a fix writing one back does (`concepts-002`, `concepts-006`) — the BDD judge reads the log, not the terminal, and `stdout_regex` matches stdout alone. All go through `runner.RefuseStartup`, a container `cmd` cannot build among them (`containerFor`), except two whose messages Scenarios pin: the `docs:` check (`Refusing to start: checklist documents unsatisfiable`, inline in `validateSpec`) and a document key `cmd` cannot resolve (`Refusing to start: document unresolvable`, `refuseUnresolvedDoc`). An error already diagnosed by the code that produced it is wrapped in `runner.Reported` so it is not announced twice. A walk that stops mid-way (a Prompt fixed more often than `config.max_apply_attempts` allows, a failed AI turn, a check that cannot answer) is logged once more by `runner.Run` as `level=ERROR msg="Walk stopped"` with the command and the error, since cobra prints the error only to stderr (`fix-loop-bounds-002`).

## Model tiers and providers

The engine drives two agent CLIs — `claude`, `codex` — picked per checklist role. `engine.models` binds tiers (`xhigh`, `high`, `coder`, `quick`) to `"<cli>:<model>"` (split on the FIRST colon only); `engine.default_prompt_model` / `default_fix_model` / `default_apply_model` name each role's fallback tier. Per-cell resolution: prompt override (`model:`/`fix_model:`/`apply_model:`) → checklist `engine:` block → `engine.default_<role>_model`. Anything unresolvable is a startup error, never a silent substitution.

- **Turn lifetime (ADR-0025):** the router adds no deadline to any role or CLI. Every turn runs with the caller's context; cancellation stops its process group and descendants and remains fatal. No time, turn, token or cost budget is added to requests, prompts, checklists or templates.
- `internal/domain/models/provider/` owns the vocabulary (`ModelRef`, `Tier`, `Registry`); the registry is validated once in `bootstrap.newAIRouter`. `adapters/ai/router.go` is the only `ports.AIPort` implementation.
- `ExecutionMode.WriteGlobs()` supplies the write patterns for Claude's guard and codex's apply profile; `AllowsBash()` also guides Claude tooling. The router independently selects codex apply confinement by role, leaving plan and validation read-only.
- The fix generator and applier never see the prompt; the evaluator resolves their tiers and carries them on `ValidationResult.FixModelTier`/`ApplyModelTier`.
- **Claude build-code writer (2.1.285, ADR-0022):** only this applier requests `TurnOptions.ClaudeWriter`. The wrapper uses generated `--settings`, `--restricted`, an explicit six-tool inventory (MultiEdit is named but absent in 2.1.285), default permission mode and no safe mode. `claude-guard --policy <generated JSON>` receives every PreToolUse payload and explicitly grants only canonical foreground Bash or confined file tools. Bash has no permission allow pattern; both Bash timeouts are 600000 ms. Read roots are the host, GOROOT, the architecture-declared library graph and its exact version metadata, and this session UUID's tool-results directory. A module cache inside the host stays restricted to that graph. The generated policy and library-download scratch are protected from writes. Claude's replay remains unconfined with network for model trials (ADR-0028, Q15). Searches outside the host reject ancestors of excluded module copies; Glob also checks its fixed pattern root and denies parent traversal. Writes derive from the execution mode's roots, excluding the generated settings/policy directory. User/project CLAUDE.md, automatic memory, skills, installed plugins, commands, workflows and MCP stay disabled. Default sign-in is retained because an empty config dir was signed out. The applier renders Claude foreground completion or codex native polling directly from the shipped template. Started Claude non-zero exits, error results and empty replies carry `errors.ClaudeTurnError`; only the build-code applier recovers them, with one WARN and `PostNotApplied`. Stream cost survives failed results. Start failures remain fatal. Other Claude turns retain their arguments and share the unbounded, cancellable lifetime.
- **codex applies (0.162.1, ADR-0021 and ADR-0024):** the router sets `Request.CodexApply` for every codex apply role regardless of command or tools. `TurnOptions.CodexWriter` remains build-code-only and selects replay forms and recovery. Generated per-turn `CODEX_HOME` copies only private `auth.json`; its profile denies commands access to the shared host tmp/codex-homes subtree for all turns and runs; auth.json is removed on preparation or turn completion, success or failure, and cleanup errors are reported. The profile denies every filesystem path outside the host except `:minimal` OS runtime, GOROOT, the architecture-declared library graph and exact version metadata, and the explicit runtime grants below. The module cache is denied by default with narrower library read entries; its cache/vcs subtree, protected library-download scratch, and implicit `/private/tmp`/`/private/var/tmp` scratch are denied; host roots take precedence where nested. The mode's file, directory and configured-glob roots and host tmp are writable. Existing files stay files; literal directory roots and file parents use rooted creation. Configured globs allow matching new files even without existing matches. Terminal `/**` retains its literal subtree grant; other wildcards grant the narrowest literal directory and enforce the original patterns after every turn. Newly created non-matching files are removed; a pre-existing non-matching file changed, deleted, renamed or given different permissions fails the turn with one WARN naming it. Overlapping grants authorize their union; these violations are fatal even for build code. Generated homes are excluded from comparison; malformed patterns, host-root grants and escapes refuse (ADR-0024). Source-root symlinks escaping the host are refused. Command environment inherits nothing: controlled PATH, HOME/TMPDIR/GOCACHE under host tmp, Go roots, offline proxy/sumdb, local toolchain, disabled telemetry/CGO and `-trimpath -buildvcs=false`. Optional installed node/npm/npx/docker binaries, npm's validated package, Mach-O dependencies and their installation symlinks are explicit read grants; Homebrew opt directories permit link metadata, with unrelated canonical targets denied. npm/npx JavaScript package roots require package.json naming npm and resolved bin/npm-cli.js or bin/npx-cli.js, outside the host, authentication and sensitive home roots enumerated in ADR-0024; otherwise the runtime is refused with a WARN and no link or grant. Generated runtime-bin links, offline npm cache/config, Docker config and all writable runtime state stay in scratch. No Docker daemon or socket is granted; `OPENSSL_CONF=/dev/null` avoids outside OpenSSL configuration. No outer sandbox. Generated config suppresses user config/MCP/web/history/AGENTS.md/host skills/plugins/apps; high reasoning, configured window 1050000 (1M unverified). `--json` stdout is archived separately from stderr; `-o` remains the answer. Drill audit reads commands and file changes without inferring read success. Started non-zero/empty/missing-answer outcomes carry `CodexTurnError`; build code alone preserves edits, warns once and reruns `PostNotApplied`. Start failures stay fatal. No codex stall watch. Planning and validation keep argv, environment and read-only sandbox; other commands' confined applies retain fatal failures. Cassette filtering excludes generated homes and shell/build scratch.
- **codex gotchas (verified live, codex-cli 0.162.1, #165):** `--output-schema` refuses a schema whose `required` leaves out any property, which claude accepts, so `CodexProvider` lists every property there before writing the schema file. codex writes its own answer file, so the cassette carries it: it is `-codex-answer.txt`, since a `.md` there fails alint's `text-final-newline` (codex ends its message with no newline).

## Prompt data contract

`docs/architecture/architecture.yaml` states the data each configured prompt template reads under `architecture.prompt_data`, including its source and every transformation before rendering. A change to any transformation stated there updates its `prompt_data` entry in the same change. Keep shared anchors accurate for every template using them. The field-inventory guard in `internal/infrastructure/template/prompt_inventory_internal_test.go` compares template reads with those entries in both directions; it does not verify shaping.

## Build identity

`version` is a plain terminal answer: exactly `true-bdd version <version> commit <commit>` and a newline, without loading configuration, installing logging or creating files or directories. Commands that install the engine log, including `init`, emit one INFO `Engine started` record with `version` and `commit` before any other record. `engine-entry-005-version-reports-build` pins the file-free answer; `build-tests-files-002-stale-test-regenerated` pins the start record without an AI turn.

## Package notes

- The engine owns all code it uses from this repository: `internal/infrastructure/{console,disk,logging,shell,enginelog}` are its IO channels and log vocabulary; `internal/infrastructure/cli/` exposes the spawn vocabulary and typed wrappers `claude`, `codex`, `git` (environment scrubbing), `gotool`, `spec` and `truebdd`. Only the shell imports `os/exec`; only those explicitly named wrappers import the shell. Logs use the engine's logging channel, files its disk channel and terminal descriptors its console channel. The domain imports none of these implementations. `pkg/` remains independent code for tests and tooling and the engine never imports it. The `Engine owns repository code` gate scans all engine Go imports, including tests and hidden build variants; the drill records its result in `engine_imports`. CLI argv/stdin remain the byte contract stated in `docs/architecture/architecture.yaml` (`dependencies[].invocation`); change an invocation and that statement together.
- `internal/app/generators/scenariogen/` renders registry → Go test. `BuildPlan` refuses the whole registry before writing a byte; `Render` always runs `format.Source`; `Write` refuses a target without the generated marker. Its template is `//go:embed`ed (it must compile against bddgo's API), not under `templates/`.
- `internal/infrastructure/stepcoverage/` parses each suite's `steps/` package and resolves which registry steps bind to nothing. Its mirror of bddgo's resolver is checked by running both: with the suites green, engine and runtime must agree on every scenario.
- `internal/app/checks/` holds the built-in checks a `D:` prompt names (ADR 0015). A command's `runner.Spec.Checks` is the `checks.Set` of checks that read its Item (`checks.ForScenarios` for `scen check`, `checks.ForStories` for `us refine`), so a new check is one entry there; a command with none refuses every `D:`. The runner answers a `D:` Cell itself (`runner/check_cell.go`), never through the evaluator, and saves the verdict as the JSON a schema-bearing turn leaves, under the Cell's usual artifact names, so the coverage census credits both alike. `PromptWithContext.Index` is the FILE position: `D:` prompts walk first (`walkOrder`), but artifacts and report rows keep file numbering — so inserting a `D:` above existing `Q:`s renumbers them, changes their result paths, and re-hashes every cassette of that checklist; append it instead. A check's `Docs` lists the document keys it reads, and a `D:` whose effective `docs:` omits one is a startup refusal: the check would find nothing there and pass unchecked.
- The closure checks `declared-terms`, `term-mappings`, `concept-bindings` and `step-definitions`, with `public-interface` (#239) beside them in `internal/app/checks`: `internal/infrastructure/product` reads the product document's `concepts:` and `glossary:`, the only parts the engine decodes, and refuses the retired `catalogue` key; `internal/domain/models/catalogue` keeps the step vocabulary as data (blocks, `catalogue.Step`s of `RegistryScenario.CheckedSteps`, concept specs, term reviews and the pattern check). All four closure checks share `checks.closureCheck`: a product declaring no `concepts:` passes every Scenario as "not checked: the product document declares no concepts"; otherwise every Scenario is checked, a Story claiming it or not. `declared-terms` and `term-mappings` hold every declared concept's `terms` to the glossary and to the architecture's `terms:` (`architecture.LoadTermMappings`, `catalogue.ReviewTerms`/`ReviewMappings`), each finding naming its concept once (`then concept 'answer' declares "reply", which the glossary does not define`, pinned by `scen-check-fix-002`). `concept-bindings` holds every `architecture.concepts` binding to a declared concept, one binding per concept, block and service, and references its service's Public interface declares, or a UI service's intent. `step-definitions` is `reviewConceptDefinitions`: each non-model step of the Scenario binds one definition whose `//truebdd:concept` record (`stepskeleton.Concepts`, matched by registered pattern) names a concept the product declares under the step's block; two bindings, no record, another block's or an undeclared concept fail, and an unbound step is reported as a gap. A check's error stops the walk and is logged as `msg="Check could not answer"`, since cobra prints it only to stderr. `scen check --fix` writes a closure fix to the term documents, the product and the architecture document, and a model Prompt's fix to the product document or the Scenario's own Registry entry: `commands/fix_documents.go` seeds `tmp/<run>/<key>.yaml` per term document the host has and one for the Registry, the applier edits that copy in EditMode (codex apply confinement grants the mode's scratch writes; an existing single-file source root stays a file), and `PostFix` puts a changed copy over the document once it parses and its concepts and glossary, its word mapping, or its Scenarios (the same ids) load; a `public-interface` or `concept-bindings` fix commits the architecture and the interface documents through `commitInterfaceFix`, which refuses a copy declaring `architecture.phrases`. A changed Registry is reloaded into every walked subject in place, so the restarted walk asks about the Scenario as it now reads. A fix stands only once a walk converges: a run that ends otherwise (out of walks, the exit choice, a walk that stopped) puts every document it wrote back as it read before the walk (`commands.fixLedger`, `fix-loop-bounds-004`). Its fix-generator template renders `FailedCheck.Context`, the only place a `D:` finding reaches the model; the other commands' templates do not. Each scen-check fix template chooses its wording by the failed result: a concept judgement (`Judgement`), then `public-interface`, then a model `Q:` Prompt (`eq .FailedCheck.Check ""`, the applier's `eq .Check ""`) with the Scenario-rewriting text and the Registry's working copy, else the concept document text naming the glossary for `declared-terms`, the word mapping for `term-mappings` and `architecture.concepts` for `concept-bindings`. The closure applier templates name `architecture.terms:` only when `.Subject.Writes "architecture_yaml"`. `us refine` walks a `template.StoryRefineData` (the Story embedded, so its templates read the Story's fields unchanged) and holds no built-in check: its `Spec.Checks` is empty, and its concept judgements' fixes seed the term documents' working copies as `scen check` does, its applier running in EditMode, `refinePostFix` committing a product working copy for a concept confirmation and reading a Story body for a rewrite. Its four `us-checklist.fix-*` templates branch only on a concept judgement, the `Q:` text otherwise.
- `internal/infrastructure/architecture/loader.go` decodes ONLY `testing:` (`framework`, `config`, `commands`, `libraries`), each service's `name`/`path`/`language`/`writable`/`libraries`/`public_interface` and `concepts:`; it refuses the retired `architecture.phrases` (`ErrPhrasesRetired`), while `term_mappings_loader.go` reads `terms:` and `concept_bindings_loader.go` `concepts:` with duplicates kept. Other sections under `architecture:` stay undecoded — only `go run ./scripts/cmd/linters schemas` would notice a typo there.
- **A new checklist costs a fixture run per branch.** `pkg/testkit/cmd/coverage` requires the checked-in `baseline.yaml` to cover EVERY (prompt × pass/fail) branch of every shipped checklist (`assertBaselineComplete`), and `TestUniverseCensus` pins the Q/F/branch counts — so an 8-prompt checklist needs one fixture scenario designed to pass all 8 and one designed to fail all 8. The walk continues past a failure when no `F:` exists (`CellFailedNoFix` → `idx++`), which is what lets one run cover eight branches. A prompt with an `F:` has a third, `fix`, branch, which only a `--fix` run that fails the prompt, applies the fix and converges covers: the `scen-check` quality and model closure prompts get one recorded fixture each, narrowed to that prompt by `checklist-prompts.yaml` (one per pinned prompt in `declaredSelections`). A fixture's own checklist credits a shipped prompt when its question or check, rationale, `F:` and docs are the shipped ones verbatim (`EvalKey`), which is how `scen-check-fix-002` to `-004`, `public-interface-fix` and `concepts-fix-operation` cover the five closure checks' fix branches: copy a shipped prompt into a fixture's checklist byte for byte. Regenerate after a full replay: `go run github.com/ondatra-ai/true-bdd/pkg/testkit/cmd/coverage -session <s> -write-baseline`. `Baseline.Write` is fail-closed on HARD diagnostics and `-rebaseline` does NOT lift that; eight fixtures (`build-code-command-not-executable`, `build-code-jest-no-tests`, `us-apply-{malformed-scenarios,missing-story,shared-prefix,story-id-mismatch,story-without-acs,unshaped-criterion-id}`) emit one every session, so delete their run dirs from the scanned session first — they contribute no coverage, having no AI turns.
- `true-bdd/` schemas are host lint contracts, not engine inputs — only `go run ./scripts/cmd/linters schemas` enforces them, though the engine reads the product document's `concepts:` and `glossary:` and the architecture's `terms:` and `concepts:` itself, and refuses one it cannot decode or one still declaring the retired template form; the pairing key is the WHOLE document key, underscores included (`architecture_yaml-schema.yaml`), and a schema whose key names no document HARD-FAILS the gate.

## Run-only model overrides

Every AI-turn command (`us refine`, `us apply`, `scen check`, `build steps`, `build code`) declares repeatable `--model <tier>=<cli>:<model>` flags. Lazy bootstrap validates the loaded tier table and role defaults first, then validates all overrides against declared tiers using the config's model-reference parser; duplicate tiers, undeclared tiers and invalid references refuse startup with exit 1 before any turn. The resulting in-memory registry changes only the named tiers, preserving Prompt → checklist → role-default selection. Each override logs once at INFO with `msg="Model tier overridden"`, `tier`, `from`, `to`. Apart from logs no override is written to a file, and none enters a spawned process's environment; the resolved model travels as its CLI argument. The drill accepts only repeated `--model` value pairs after `build steps --fix` or `build code --fix`, and none after `build tests --fix`; it keeps them in the run's argument record and forwards values unchanged through typed wrapper options. Engine startup owns semantic validation; deterministic `build tests` has no `--model` flag.

**Concept judgements (#257):** `with.concepts` selects link, group, bindings, sketch or words on a Q Prompt. A host declaring no concepts omits link/group/binding/word cells and gets Prompt 12's plain text. Concept links are current-walk Item evidence, never Registry data. Word judgements require that walk's successful link and a complete verdict for every linked meaning; their Product Owner fixes commit only the product document. Newly declared terms wait for the Architect's later `D: term-mappings` fix in `scen check`, never in refinement. The evaluator saves the raw model answer separately and saves the derived canonical verdict as response/result JSON. Fix templates branch first on `Judgement`, then on the failed check; proposals carry the whole Item and `**Actual:**` for coverage attribution. Refinement commits product working copies for concept confirmations and reads a Story body for rewrites; Scenario fixes commit the architecture and needed Public interface copies as well.
