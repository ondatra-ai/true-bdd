# Engine Internals

## build tests / build code, in depth

- `build tests` — Stage 1 is deterministic codegen (one `func Test<Key>` per scenario, the key in CamelCase, into its `path:` file; written by `--fix`, verified by regenerate-and-compare without it). Stage 2 resolves which steps bind to nothing and walks **only** the scenarios with gaps — a converged repo dispatches zero AI turns. "Executable" = every Given/When/Then step binds to exactly one step definition in the tree that owns it (`tests/<service>/`, for the scenario's own `service:` — there are no suite entries; definitions under `tests/<service>/steps/`), except `llm:`/`judge:` steps, which a model runs and must never be given a definition. With `--fix`, each gap drives a Claude-mediated loop authoring the missing step definition; the registry is never modified by the run. When the product document declares a catalogue, Prepare first holds EVERY Registry step to it, claimed by a Story or not, with the `step-phrases` review (`checks.ReviewPhrases`, from `commands/build_tests_phrases.go`), after the plan builds and before the scan, codegen and any AI turn: a step matching no template, several, or one of another block (or a malformed template, repeated per Scenario) is a `Refusing to start` whose error carries those lines (`build-tests-refusals-005`). A clean Registry logs `msg="Step phrases checked"`; no product document, or no `catalogue:` key, logs `msg="Step phrases not checked"` and walks as before (`build-tests-refusals-006`). Under `--fix`, when the product document declares a catalogue, Prepare also reads the spec of every Scenario's unbound steps before codegen (`commands/build_tests_spec.go`, `(*Catalogue).Specify`): the phrase each of its own gaps matches, every phrase the other gaps of its suite reach, and each declared word with its glossary `means` and its `architecture.terms` mapping, logged as `msg="Unbound steps specified"`; a catalogue, glossary or word mapping it cannot decode refuses the run there (`build-tests-steps-007`), and no product document, or no `catalogue:` key, reads nothing. It rides on the walked Item (`commands.BuildTestsItem`, the Registry entry embedded so the templates read its fields unchanged) into a section of the fix-generator templates guarded by `.Subject.Spec.Declared`, so a host with no product document or no catalogue renders byte-identical prompts and `build-tests-steps-001` keeps replaying; `build-tests-steps-006` records a walk authoring from the spec. Step coverage's gaps carry each step's block and text (`catalogue.Step`). Coverage narrowing is IN-PROCESS and always on (which replaced a subprocess): the engine parses `<suite root>/steps/` — `path.Dir` of a scenario's `path:`, never the service's name — folding each `suite.Step` pattern from constants. It NEVER skips: a pattern that will not constant-fold is a refusal naming file, line and expression, one that will not compile fails the whole answer, and a step matched by two definitions is a refusal, never a gap. An absent `steps/` dir is zero definitions, not an error, so a host with none walks everything. The answer keys on which scenarios it **examined**: one absent from `examined` is walked; an empty gap list alone means nothing. The scan runs BEFORE codegen — it reads a tree codegen never writes — so a refusal leaves the working tree untouched. After each applied fix, `commands.buildTestsExecution` hashes the step packages and runs each changed package's currently bound Registry Scenarios, including initially bound peers, through `testing.commands.replay`; the existing Go runner appends an anchored name filter, keeping the command and its working directory. When `testing.prebuilt_engine_arg` is declared, verification appends it as one argv element after splitting the literal replay command, substituting `{engine_bin}` exactly once with the running binary's absolute, symlink-resolved path. The host runner must consume it and skip building service source; this repository's harness consumes `-engine-bin`. The architecture loader refuses empty declarations or a placeholder count other than one before any runner or AI turn. Hosts without the field and `build code` retain their existing commands. A missing or skipped selected test cannot pass; pass evidence must name its owning Go package. Every Scenario in a changed package remains accounted for: one that becomes unbound fails with its missing steps, even if it was initially bound or failed an earlier replay. A failure clears only when that Scenario passes replay. A runtime failure overrides the binding verdict and reaches the fix-generator template as `.Subject.Failures`, until execution passes or `config.max_apply_attempts` is reached. After a `--fix` walk the generated files are re-verified; only then is `BUILD TESTS COMPLETE` announced.
- `build code` — starts every outer walk with full discovery through `testing.commands.replay`, yielding zero Items or one whole failing set (`commands.BuildCodeItem`). Its `tests-pass` built-in `D:` Prompt answers through `runner/check_cell.go`, without a validation turn; all latest member verdicts must pass. The fix turn proposes one plan naming changes, files and served tests. The apply turn is the writer: it gets the same set, deduplicated phrases and words, all matched Scenarios and steps, Specification paths, declared service edit roots, and crush or codex whole/selected replay forms. It reads the Specification and harness, implements the service, tests each part and every set member, and reports changes and observed passes. No prompt budget is stated. Every completed apply (including `applied: false` and the terminal attempt) reruns the remaining set in `PostFix`/`PostNotApplied`, in one framework runner start. A successful provider response missing the result block (`ErrFixApplierNoContent`) follows `PostNotApplied` only for `build code`, keeps files and logs one WARN carrying the result path. Started crush writer turns stopped by the response watch, exiting non-zero or returning empty/whitespace-only output carry `errors.CrushTurnError` and follow `PostNotApplied`, preserving files and rebuilding grouped evidence for the next plan. The watch logs the stalled outcome once at WARN; the runner logs other failed writer outcomes once at WARN. Start failures, engine refusals before spawning, other commands and roles, and claude provider failures retain fatal handling; malformed extracted blocks and missing `applied` retain their existing handling in every command. The writer ends its final message with the confirmation block in the message itself; the engine saves the block at its heading's path, which the writer never writes. Selectors are joined by alternation; Go `<build>` or Playwright `<startup>` makes the rerun unfiltered. Members need their own passing result; missing/skipped results stay failing with a did-not-run finding. Passing members leave; grouped evidence uses build-tests runtime normalization but retains the whole first output and every member id. `BeforeEvaluate` leaves the verdict to `D:`. The walker attempt counter and outer bound are unchanged: allowance two still permits three applies; membership changes never reset the same Item's counter. The terminal apply is rerun but still fails at the bound even if the rerun passed. Fresh outer discovery catches previously green regressions. Exit ends the Item. Optional Specification documents warn and are omitted when unavailable; exact module-aware Go identities alone match Registry Scenarios. The mandatory `testing.commands: {record,replay,live}` block has no built-in defaults; native machine-output flags and config-directory cwd are retained by engine runners. Static refusals precede subprocesses; spawn-only errors report `Cannot run test suite` / `Cannot run suite` as `runner.Reported`. Write roots are all declared service paths; tests and documents are never edited. Document commands still reject `applied: false` before their commit hooks.

**Startup refusals**: every command reports precondition failures as `Cannot start: …` on stdout plus a `Refusing to start` slog record — the BDD judge reads the log, not the terminal, and `stdout_regex` matches stdout alone. All go through `runner.RefuseStartup`, a container `cmd` cannot build among them (`containerFor`), except two whose messages Scenarios pin: the `docs:` check (`Refusing to start: checklist documents unsatisfiable`, inline in `validateSpec`) and a document key `cmd` cannot resolve (`Refusing to start: document unresolvable`, `refuseUnresolvedDoc`). An error already diagnosed by the code that produced it is wrapped in `runner.Reported` so it is not announced twice. A walk that stops mid-way (a Prompt fixed more often than `config.max_apply_attempts` allows, a failed AI turn, a check that cannot answer) is logged once more by `runner.Run` as `level=ERROR msg="Walk stopped"` with the command and the error, since cobra prints the error only to stderr (`fix-loop-bounds-002`).

## Model tiers and providers

The engine drives three agent CLIs — `claude`, `crush`, `codex` — picked per checklist role. `engine.models` binds tiers (`xhigh`, `high`, `coder`, `quick`) to `"<cli>:<model>"` (split on the FIRST colon only); `engine.default_prompt_model` / `default_fix_model` / `default_apply_model` name each role's fallback tier. Per-cell resolution: prompt override (`model:`/`fix_model:`/`apply_model:`) → checklist `engine:` block → `engine.default_<role>_model`. Anything unresolvable is a startup error, never a silent substitution.

- `internal/domain/models/provider/` owns the vocabulary (`ModelRef`, `Tier`, `Registry`); the registry is validated once in `bootstrap.newAIRouter`. `adapters/ai/router.go` is the only `ports.AIPort` implementation.
- `ExecutionMode` is the single permission source for all three CLIs — `WriteGlobs()`/`AllowsBash()` project it onto crush's guard and codex's `-s` sandbox.
- The fix generator and applier never see the prompt; the evaluator resolves their tiers and carries them on `ValidationResult.FixModelTier`/`ApplyModelTier`.
- **crush gotchas (verified live):** it silently ignores an unknown model pinned in config (so the model is always passed via `-m`), and it fails OPEN when a hook cannot run (`verifyCrushGuardEnforces` probes the guard before every turn). `true-bdd crush-guard` is the hidden `PreToolUse` write gate, also confining `view`, `ls`, `grep`, `glob` and `diagnostics` to the policy's absolute `read_root` (the project working directory); a missing root is refused and a relative root is malformed. Every engine execution mode disallows `Bash` and keeps `allow_bash` false. Only `build code --fix`'s apply mode carries a crush-only replay grant (`test_command`, `test_selector`, `test_dir`): exact canonical command or one single-quoted selector, in the resolved suite directory. Its generated tools include `bash`, `job_output`, `job_kill`; job tools require that command. `testrunner.CanonicalReplayCommand` removes machine output and quotes argv; a single quote, newline or NUL withholds the grant with one warning. Claude permissions stay unchanged; codex build-code writers use ADR-0021's profile. It is wired through a generated config dir via `CRUSH_GLOBAL_CONFIG`; the host's `.crush.json` is never touched.
- **codex build-code writer (0.162.1, ADR-0021):** the applier sets `TurnOptions.CodexWriter` only for this command's codex apply; the router also checks role and CLI. Generated per-turn `CODEX_HOME` copies only private `auth.json`; its profile denies commands access to the shared host tmp/codex-homes subtree for all turns and runs; auth.json is removed on preparation or turn completion, success or failure, and cleanup errors are reported. The profile denies every filesystem path outside the host except `:minimal` OS runtime, GOROOT and GOMODCACHE. Both ondatra-ai module trees, including downloads, the whole module cache/cache/vcs subtree, and implicit `/private/tmp`/`/private/var/tmp` scratch are denied; host roots take precedence where nested. Service edit roots and host tmp are writable. Source-root symlinks escaping the host are refused. Command environment inherits nothing: controlled PATH, HOME/TMPDIR/GOCACHE under host tmp, Go roots, offline proxy/sumdb, local toolchain, disabled telemetry/CGO and `-trimpath -buildvcs=false`. No outer sandbox. Generated config suppresses user config/MCP/web/history/AGENTS.md/host skills/plugins/apps; high reasoning, configured window 1050000 (1M unverified). `--json` stdout is archived separately from stderr; `-o` remains the answer. Drill audit reads commands and file changes without inferring read success. Started non-zero/empty/missing-answer outcomes carry `CodexTurnError`; build code alone preserves edits, warns once and reruns `PostNotApplied`. Start failures stay fatal. No codex stall watch. Other turns keep argv, environment and sandbox; crush prompt bytes stay unchanged. Cassette filtering excludes generated homes and shell/build scratch.
- **codex gotchas (verified live, codex-cli 0.162.1, #165):** `--output-schema` refuses a schema whose `required` leaves out any property, which claude accepts, so `CodexProvider` lists every property there before writing the schema file. codex writes its own answer file, so the cassette carries it: it is `-codex-answer.txt`, since a `.md` there fails alint's `text-final-newline` (codex ends its message with no newline).
- **crush response watch (v0.97.1, ADR-0020):** only the build-code applier sets `TurnOptions.WatchWriterResponse`, carried into router `Request.WatchWriterResponse`; all other commands and roles are unwatched. The wrapper reads the generated `options.data_directory/logs/crush.log`. A JSON `ModelProvider called` record opens one response; the next record closes it, with `Hook completed` opening untimed tool execution. A response open for ten minutes kills the turn's process group and logs `Writer response stalled` once at WARN with `label`, `minutes`, `log_path`. No model record means no timer. This deliberately bounds one response, not the turn; no prompt, checklist or template states the bound.
- **crush config discovery walks UP from cwd and merges every `.crush.json` it finds**, hooks additively — a root config would hijack every fixture's apply turn. Never add a tracked `.crush.json`/`crush.json` at the repo root.

## Prompt data contract

`docs/architecture/architecture.yaml` states the data each configured prompt template reads under `architecture.prompt_data`, including its source and every transformation before rendering. A change to any transformation stated there updates its `prompt_data` entry in the same change. Keep shared anchors accurate for every template using them. The field-inventory guard in `internal/infrastructure/template/prompt_inventory_internal_test.go` compares template reads with those entries in both directions; it does not verify shaping.

## Package notes

- `internal/infrastructure/cli/{codex,crush,truebdd}` are the spawn wrappers only the engine uses, so they live here rather than in `pkg/cli/` and a rebuild regenerates them; they are the only engine packages the lint rules let import `pkg/shell`. The crush and codex argv and stdin they produce, and the claude argv `ClaudeProvider` builds through `pkg/cli/claude` (tools per execution mode, `--permission-mode acceptEdits`, the two `--json-schema` bodies), are stated in `docs/architecture/architecture.yaml` (`dependencies[].invocation`), because replay hashes both: change the wrapper and that statement together, and a crush change re-records every crush cassette.
- `internal/app/generators/scenariogen/` renders registry → Go test. `BuildPlan` refuses the whole registry before writing a byte; `Render` always runs `format.Source`; `Write` refuses a target without the generated marker. Its template is `//go:embed`ed (it must compile against bddgo's API), not under `templates/`.
- `internal/infrastructure/stepcoverage/` parses each suite's `steps/` package and resolves which registry steps bind to nothing. Its mirror of bddgo's resolver is checked by running both: with the suites green, engine and runtime must agree on every scenario.
- `internal/app/checks/` holds the built-in checks a `D:` prompt names (ADR 0015). A command's `runner.Spec.Checks` is the `checks.Set` of checks that read its Item (`checks.ForScenarios` for `scen check`, `checks.ForStories` for `us refine`), so a new check is one entry there; a command with none refuses every `D:`. The runner answers a `D:` Cell itself (`runner/check_cell.go`), never through the evaluator, and saves the verdict as the JSON a schema-bearing turn leaves, under the Cell's usual artifact names, so the coverage census credits both alike. `PromptWithContext.Index` is the FILE position: `D:` prompts walk first (`walkOrder`), but artifacts and report rows keep file numbering — so inserting a `D:` above existing `Q:`s renumbers them, changes their result paths, and re-hashes every cassette of that checklist; append it instead. A check's `Docs` lists the document keys it reads, and a `D:` whose effective `docs:` omits one is a startup refusal: the check would find nothing there and pass unchecked.
- The closure checks `step-phrases`, `declared-terms`, `term-mappings` and `step-definitions` (spike #133's catalogue): `internal/infrastructure/product` reads the product document's `catalogue:`, role names and `glossary:`, the only parts the engine decodes; `internal/domain/models/catalogue` compiles each template to an anchored regexp and reviews a run of `catalogue.Step`s (block plus keyword-less text, from `RegistryScenario.Phrases`), so `build tests` and `us refine` can reuse it on their own Items. `Declarations` lists the (template, term) pairs of the steps that match exactly one template, which `ReviewTerms` holds to the glossary. `term-mappings` holds the same pairs to the architecture's `terms:` (`architecture.LoadTermMappings`, `ReviewMappings`), and `step-definitions` holds the templates to the suite's step definitions: `stepcoverage.LoadSuite` folds `StepsDir(path)` as `Scan` does and `Suite.Bind` lists every definition a text matches, and `(*Catalogue).Correspond` relates templates and definitions over the steps of every claimed Scenario sharing that suite, which is why `ScenarioCheckData.Registry` carries the whole Registry whatever ids were selected. A check's error stops the walk and is logged as `msg="Check could not answer"`, since cobra prints it only to stderr. All four closure checks share `checks.activation`: no `catalogue:` key, or a Scenario with empty `user_stories`, passes as "not checked". `scen check --fix` writes a closure fix to the term documents, the product and the architecture document, and a model Prompt's fix to the product document or the Scenario's own Registry entry: `commands/fix_documents.go` seeds `tmp/<run>/<key>.yaml` per term document the host has and one for the Registry, the applier edits that copy in EditMode (a single file cannot be granted: `sourceRootGlob` makes it `<file>/**`), and `PostFix` puts a changed copy over the document once it parses and its catalogue and glossary, its word mapping, or its Scenarios (the same ids) load; a changed Registry is reloaded into every walked subject in place, so the restarted walk asks about the Scenario as it now reads. A fix stands only once a walk converges: a run that ends otherwise (out of walks, the exit choice, a walk that stopped) puts every document it wrote back as it read before the walk (`commands.fixLedger`, `fix-loop-bounds-004`). Its fix-generator template renders `FailedCheck.Context`, the only place a `D:` finding reaches the model; the other commands' templates do not. Each of the four fix templates opens on `eq .FailedCheck.Check ""` (the applier's on `eq .Check ""`, which the runner fills from the failed result): a `Q:` Prompt's fix gets the Scenario-rewriting text and the Registry's working copy, and the `else` branch holds the closure text byte for byte. Inside it, `FailedCheck.Check` (the `D:` check's name) describes the glossary for a `declared-terms` fix and the word mapping for a `term-mappings` one, keeping the `step-phrases` prompt byte-identical: a new check's guidance goes in its own branch, or the cassettes of `scen-check-fix-001`, `-002` and `-003` re-hash. The closure applier templates name `architecture.terms:` only when `.Subject.Writes "architecture_yaml"`, which no `step-phrases` or `declared-terms` fixture has. `us refine` walks a `template.StoryRefineData` (the Story embedded, so its templates read the Story's fields unchanged) and offers only `step-phrases`, which holds every acceptance criterion's steps to the catalogue, one context line per criterion, whenever a catalogue is declared: there is no claiming for a Story. Under `--fix` it seeds the term documents' working copies as `scen check` does, its applier runs in EditMode, and a failed `D:`'s fix goes through `Spec.PostCheckFix`, which commits the changed copy and keeps the Story's version, instead of `PostFix`, which reads the applier's reply as the next Story body. Its four `us-checklist.fix-*` templates branch on the failed check the same way, the `Q:` branch byte for byte the old text (us-refine-fix-002 replays across the change).
- `internal/infrastructure/architecture/loader.go` decodes ONLY `testing:` (`framework`, `config`, `commands`, `prebuilt_engine_arg`) and each service's `name`/`path`/`language`, and `term_mappings_loader.go` only `terms:`; everything else under `architecture:` stays undecoded — only `go run ./scripts/cmd/linters schemas` would notice a typo there.
- **A new checklist costs a fixture run per branch.** `pkg/testkit/cmd/coverage` requires the checked-in `baseline.yaml` to cover EVERY (prompt × pass/fail) branch of every shipped checklist (`assertBaselineComplete`), and `TestUniverseCensus` pins the Q/F/branch counts — so an 8-prompt checklist needs one fixture scenario designed to pass all 8 and one designed to fail all 8. The walk continues past a failure when no `F:` exists (`CellFailedNoFix` → `idx++`), which is what lets one run cover eight branches. A prompt with an `F:` has a third, `fix`, branch, which only a `--fix` run that fails the prompt, applies the fix and converges covers: the `scen-check` quality and model closure prompts get one recorded fixture each, narrowed to that prompt by `checklist-prompts.yaml` (one per pinned prompt in `declaredSelections`). A fixture's own checklist credits a shipped prompt when its question or check, rationale, `F:` and docs are the shipped ones verbatim (`EvalKey`), which is how `scen-check-fix-001` to `-004` cover the four closure checks' fix branches: copy a shipped prompt into a fixture's checklist byte for byte. Regenerate after a full replay: `go run ./pkg/testkit/cmd/coverage -session <s> -write-baseline`. `Baseline.Write` is fail-closed on HARD diagnostics and `-rebaseline` does NOT lift that; seven fixtures (`build-code-command-not-executable`, `us-apply-{malformed-scenarios,missing-story,shared-prefix,story-id-mismatch,story-without-acs,unshaped-criterion-id}`) emit one every session, so delete their run dirs from the scanned session first — they contribute no coverage, having no AI turns.
- `true-bdd/` schemas are host lint contracts, not engine inputs — only `go run ./scripts/cmd/linters schemas` enforces them, though the engine reads the product document's `catalogue:`, role names and `glossary:` and the architecture's `terms:` itself, and refuses one it cannot decode; the pairing key is the WHOLE document key, underscores included (`architecture_yaml-schema.yaml`), and a schema whose key names no document HARD-FAILS the gate.
