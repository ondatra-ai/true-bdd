# Engine Internals

## build tests / build code, in depth

- `build tests` — Stage 1 is deterministic codegen (one `func Test<Key>` per scenario, the key in CamelCase, into its `path:` file; written by `--fix`, verified by regenerate-and-compare without it). Stage 2 resolves which steps bind to nothing and walks **only** the scenarios with gaps — a converged repo dispatches zero AI turns. "Executable" = every Given/When/Then step binds to exactly one step definition in the tree that owns it (`tests/<service>/`, for the scenario's own `service:` — there are no suite entries; definitions under `tests/<service>/steps/`), except `llm:`/`judge:` steps, which a model runs and must never be given a definition. With `--fix`, each gap drives a Claude-mediated loop authoring the missing step definition; the registry is never modified by the run. When the product document declares a catalogue, Prepare first holds EVERY Registry step to it, claimed by a Story or not, with the `step-phrases` review (`checks.ReviewPhrases`, from `commands/build_tests_phrases.go`), after the plan builds and before the scan, codegen and any AI turn: a step matching no template, several, or one of another block (or a malformed template, repeated per Scenario) is a `Refusing to start` whose error carries those lines (`build-tests-refusals-005`). A clean Registry logs `msg="Step phrases checked"`; no product document, or no `catalogue:` key, logs `msg="Step phrases not checked"` and walks as before (`build-tests-refusals-006`). Under `--fix`, when the product document declares a catalogue, Prepare also reads the spec of every Scenario's unbound steps before codegen (`commands/build_tests_spec.go`, `(*Catalogue).Specify`): the phrase each of its own gaps matches, every phrase the other gaps of its suite reach, and each declared word with its glossary `means` and its `architecture.terms` mapping, logged as `msg="Unbound steps specified"`; a catalogue, glossary or word mapping it cannot decode refuses the run there (E2E-131), and no product document, or no `catalogue:` key, reads nothing. It rides on the walked Item (`commands.BuildTestsItem`, the Registry entry embedded so the templates read its fields unchanged) into a section of the fix-generator templates guarded by `.Subject.Spec.Declared`, so a host with no product document or no catalogue renders byte-identical prompts and E2E-016 keeps replaying; E2E-130 records a walk authoring from the spec. Step coverage's gaps carry each step's block and text (`catalogue.Step`). Coverage narrowing is IN-PROCESS and always on (which replaced a subprocess): the engine parses `<suite root>/steps/` — `path.Dir` of a scenario's `path:`, never the service's name — folding each `suite.Step` pattern from constants. It NEVER skips: a pattern that will not constant-fold is a refusal naming file, line and expression, one that will not compile fails the whole answer, and a step matched by two definitions is a refusal, never a gap. An absent `steps/` dir is zero definitions, not an error, so a host with none walks everything. The answer keys on which scenarios it **examined**: one absent from `examined` is walked; an empty gap list alone means nothing. The scan runs BEFORE codegen — it reads a tree codegen never writes — so a refusal leaves the working tree untouched. After a `--fix` walk the generated files are re-verified.
- `build code` — discovers failing tests by running `testing.commands.replay`, and walks each failure against the `build-code` checklist. With `--fix`, Claude edits production source until the test passes; test files and the registry are never modified. `testing:` carries a mandatory `commands: {record, replay, live}` block, once for the whole repository — there is **no built-in invocation**; an incomplete block is a startup refusal, never a substituted default. Each command is framework-native including its machine-readable flag, runs from the directory holding `testing.config:` (one working directory per repository — playwright resolves `testDir` from there), and gets only a name filter appended on re-run. The fix applier's write roots are EVERY declared service's `path:` (`servicePaths`): with no suite to name one service, the walk's own failure decides which tree it edits. Everything statically checkable is checked in a pre-pass before the first subprocess; what only a spawn can reveal surfaces as `Cannot run test suite` / `Cannot run suite` on stdout, marked `runner.Reported` so the generic refusal stays silent. Negative-coverage fixtures live at `tests/bdd-cli/fixtures/build-code-*`, each planting a *failing* test so "reported no failures" can never be confused with "had nothing to find".

**Startup refusals**: every command reports precondition failures as `Cannot start: …` on stdout plus a `Refusing to start` slog record — the BDD judge reads the log, not the terminal, and `stdout_regex` matches stdout alone. All go through `runner.refuseStartup` except the `docs:` check, which reports inline. An error already diagnosed by the code that produced it is wrapped in `runner.Reported` so it is not announced twice. A walk that stops mid-way (a Prompt fixed more often than `config.max_apply_attempts` allows, a failed AI turn, a check that cannot answer) is logged once more by `runner.Run` as `level=ERROR msg="Walk stopped"` with the command and the error, since cobra prints the error only to stderr (`fix-loop-bounds-002`).

## Model tiers and providers

The engine drives three agent CLIs — `claude`, `crush`, `codex` — picked per checklist role. `engine.models` binds tiers (`xhigh`, `high`, `coder`, `quick`) to `"<cli>:<model>"` (split on the FIRST colon only); `engine.default_prompt_model` / `default_fix_model` / `default_apply_model` name each role's fallback tier. Per-cell resolution: prompt override (`model:`/`fix_model:`/`apply_model:`) → checklist `engine:` block → `engine.default_<role>_model`. Anything unresolvable is a startup error, never a silent substitution.

- `internal/domain/models/provider/` owns the vocabulary (`ModelRef`, `Tier`, `Registry`); the registry is validated once in `bootstrap.newAIRouter`. `adapters/ai/router.go` is the only `ports.AIPort` implementation.
- `ExecutionMode` is the single permission source for all three CLIs — `WriteGlobs()`/`AllowsBash()` project it onto crush's guard and codex's `-s` sandbox.
- The fix generator and applier never see the prompt; the evaluator resolves their tiers and carries them on `ValidationResult.FixModelTier`/`ApplyModelTier`.
- **crush gotchas (verified live):** it silently ignores an unknown model pinned in config (so the model is always passed via `-m`), and it fails OPEN when a hook cannot run (`verifyCrushGuardEnforces` probes the guard before every turn). `true-bdd crush-guard` is the hidden `PreToolUse` write gate, wired through a generated config dir via `CRUSH_GLOBAL_CONFIG`; the host's `.crush.json` is never touched.
- **crush config discovery walks UP from cwd and merges every `.crush.json` it finds**, hooks additively — a root config would hijack every fixture's apply turn. Never add a tracked `.crush.json`/`crush.json` at the repo root.

## Package notes

- `internal/infrastructure/cli/{codex,crush,truebdd}` are the spawn wrappers only the engine uses, so they live here rather than in `pkg/cli/` and a rebuild regenerates them; they are the only engine packages the lint rules let import `pkg/shell`. The crush and codex argv and stdin they produce are stated in `docs/architecture/architecture.yaml` (`dependencies[].invocation`), because replay hashes both: change the wrapper and that statement together, and a crush change re-records every crush cassette.
- `internal/app/generators/scenariogen/` renders registry → Go test. `BuildPlan` refuses the whole registry before writing a byte; `Render` always runs `format.Source`; `Write` refuses a target without the generated marker. Its template is `//go:embed`ed (it must compile against bddgo's API), not under `templates/`.
- `internal/infrastructure/stepcoverage/` parses each suite's `steps/` package and resolves which registry steps bind to nothing. Its mirror of bddgo's resolver is checked by running both: with the suites green, engine and runtime must agree on every scenario.
- `internal/app/checks/` holds the built-in checks a `D:` prompt names (ADR 0015). A command's `runner.Spec.Checks` is the `checks.Set` of checks that read its Item (`checks.ForScenarios` for `scen check`), so a new check is one entry there; a command with none refuses every `D:`. The runner answers a `D:` Cell itself (`runner/check_cell.go`), never through the evaluator, and saves the verdict as the JSON a schema-bearing turn leaves, under the Cell's usual artifact names, so the coverage census credits both alike. `PromptWithContext.Index` is the FILE position: `D:` prompts walk first (`walkOrder`), but artifacts and report rows keep file numbering — so inserting a `D:` above existing `Q:`s renumbers them, changes their result paths, and re-hashes every cassette of that checklist; append it instead. A check's `Docs` lists the document keys it reads, and a `D:` whose effective `docs:` omits one is a startup refusal: the check would find nothing there and pass unchecked.
- The closure checks `step-phrases`, `declared-terms`, `term-mappings` and `step-definitions` (spike #133's catalogue): `internal/infrastructure/product` reads the product document's `catalogue:`, role names and `glossary:`, the only parts the engine decodes; `internal/domain/models/catalogue` compiles each template to an anchored regexp and reviews a run of `catalogue.Step`s (block plus keyword-less text, from `RegistryScenario.Phrases`), so `build tests` and `us refine` can reuse it on their own Items. `Declarations` lists the (template, term) pairs of the steps that match exactly one template, which `ReviewTerms` holds to the glossary. `term-mappings` holds the same pairs to the architecture's `terms:` (`architecture.LoadTermMappings`, `ReviewMappings`), and `step-definitions` holds the templates to the suite's step definitions: `stepcoverage.LoadSuite` folds `StepsDir(path)` as `Scan` does and `Suite.Bind` lists every definition a text matches, and `(*Catalogue).Correspond` relates templates and definitions over the steps of every claimed Scenario sharing that suite, which is why `ScenarioCheckData.Registry` carries the whole Registry whatever ids were selected. A check's error stops the walk and is logged as `msg="Check could not answer"`, since cobra prints it only to stderr. All four closure checks share `checks.activation`: no `catalogue:` key, or a Scenario with empty `user_stories`, passes as "not checked". `scen check --fix` writes a closure fix to the term documents, the product and the architecture document, and a model Prompt's fix to the product document or the Scenario's own Registry entry: `commands/fix_documents.go` seeds `tmp/<run>/<key>.yaml` per term document the host has and one for the Registry, the applier edits that copy in EditMode (a single file cannot be granted: `sourceRootGlob` makes it `<file>/**`), and `PostFix` puts a changed copy over the document once it parses and its catalogue and glossary, its word mapping, or its Scenarios (the same ids) load; a changed Registry is reloaded into every walked subject in place, so the restarted walk asks about the Scenario as it now reads. Its fix-generator template renders `FailedCheck.Context`, the only place a `D:` finding reaches the model; the other commands' templates do not. Each of the four fix templates opens on `eq .FailedCheck.Check ""` (the applier's on `eq .Check ""`, which the runner fills from the failed result): a `Q:` Prompt's fix gets the Scenario-rewriting text and the Registry's working copy, and the `else` branch holds the closure text byte for byte. Inside it, `FailedCheck.Check` (the `D:` check's name) describes the glossary for a `declared-terms` fix and the word mapping for a `term-mappings` one, keeping the `step-phrases` prompt byte-identical: a new check's guidance goes in its own branch, or E2E-097's, E2E-104's and E2E-119's cassettes re-hash. The closure applier templates name `architecture.terms:` only when `.Subject.Writes "architecture_yaml"`, which no `step-phrases` or `declared-terms` fixture has.
- `internal/infrastructure/architecture/loader.go` decodes ONLY `testing:` (`framework`, `config`, `commands`) and each service's `name`/`path`/`language`, and `term_mappings_loader.go` only `terms:`; everything else under `architecture:` stays undecoded — only `go run ./scripts/cmd/linters schemas` would notice a typo there.
- **A new checklist costs a fixture run per branch.** `pkg/testkit/cmd/coverage` requires the checked-in `baseline.yaml` to cover EVERY (prompt × pass/fail) branch of every shipped checklist (`assertBaselineComplete`), and `TestUniverseCensus` pins the Q/F/branch counts — so an 8-prompt checklist needs one fixture scenario designed to pass all 8 and one designed to fail all 8. The walk continues past a failure when no `F:` exists (`CellFailedNoFix` → `idx++`), which is what lets one run cover eight branches. A prompt with an `F:` has a third, `fix`, branch, which only a `--fix` run that fails the prompt, applies the fix and converges covers: the `scen-check` quality and model closure prompts get one recorded fixture each, narrowed to that prompt by `checklist-prompts.yaml` (one per pinned prompt in `declaredSelections`). A fixture's own checklist credits a shipped prompt when its question or check, rationale, `F:` and docs are the shipped ones verbatim (`EvalKey`), which is how E2E-097, E2E-104, E2E-119 and E2E-129 cover the four closure checks' fix branches: copy a shipped prompt into a fixture's checklist byte for byte. Regenerate after a full replay: `go run ./pkg/testkit/cmd/coverage -session <s> -write-baseline`. `Baseline.Write` is fail-closed on HARD diagnostics and `-rebaseline` does NOT lift that; seven fixtures (`build-code-command-not-executable`, `us-apply-{malformed-scenarios,missing-story,shared-prefix,story-id-mismatch,story-without-acs,unshaped-criterion-id}`) emit one every session, so delete their run dirs from the scanned session first — they contribute no coverage, having no AI turns.
- `true-bdd/` schemas are host lint contracts, not engine inputs — only `go run ./scripts/cmd/linters schemas` enforces them, though the engine reads the product document's `catalogue:`, role names and `glossary:` and the architecture's `terms:` itself, and refuses one it cannot decode; the pairing key is the WHOLE document key, underscores included (`architecture_yaml-schema.yaml`), and a schema whose key names no document HARD-FAILS the gate.
